# Queue mechanisms connected to the known-input pilot

Audit date: 2026-10-28. This is a CPU-only, read-only source and artifact audit. No Python file, model, immutable prior artifact, GPU state, weight or threshold was changed. The accompanying exclusive receipt is `artifacts/predictor-queue-paper-mechanism-audit-v5-20261028-final01/report.json`.

The real pilot connects whole-horizon public arrivals, per-owner FIFO, eventwise DAG progress, fitted host release and distinct handler/parent/worker-ready boundaries. It does **not** connect the package simulator's resource-work diagnostics, batch formation/padding, recovery-risk model or observation-driven rolling forecast. The library implementations must not be reported as features executed by this pilot.

The paper names below refer to the mechanism-transfer goals already declared in `docs/predictor_v2_execution_plan_20261027.md:18`. This audit verifies project wiring; it does not reproduce those papers or inherit their accuracy, resource isolation or optimality claims.

Actual execution dispatch is `known_input_forecast_gate_v5.run_and_seal` → `forecast_gate_v3.execute_bundle` → `cuda_dag_simulator_v4.DagFullHorizonModel`. The branch at `forecast_gate_v3.py:198` selects the tools DAG engine for `provider_kind=cuda_dag_host_supply_v4`; the package `FullHorizonModel` is a different branch at `:189`. A source receipt appearing in the broad frozen closure does not mean its code ran.

`known_input_forecast_gate_v5.py:12`–`:69` checks the full source/model/training closure, all predeclared candidate/run cells, unchanged six weights, matching objective normalizers and identical public cohorts; it verifies sources again before making a seal. `known_input_native_flow_v5.py:139`–`:204` verifies that seal before collection and again after acquiring the GPU lock. These are prospective evidence boundaries, not proof of predictive accuracy. The collector enqueues the predeclared schedule and routes and does not call a forecast, batch planner, risk provider or rolling observer during measurement.

The actual DAG model keeps FIFO deques and chooses `popleft()` only when the owner has neither a running handler nor an outstanding ready delay (`cuda_dag_simulator_v4.py:37`–`:99`). It does not truncate the future request count silently; unknown templates, durations or exceeded event budget fail. Its event calendar includes every declared arrival, ready release, activity completion, parent receipt and worker-ready wakeup (`:123`–`:166`). Queue waiting is arrival to handler start, consistent with the plan's `waiting_until_handler_start` queue-depth boundary and 101 samples every 0.3 seconds.

The eventwise remaining duration is useful execution state, but it is the residual of a numerical duration hypothesis. It is neither an observed GPU cursor nor normalized resource demand. GPU nodes run at rate `1 / active GPU owners`; all ready nodes within one owner may progress concurrently. Copy/memset service is independent at rate one (`:138`–`:160`, `:194`–`:211`). This permits overlap but supplies no same-SM concurrency guarantee, SM/DRAM/L2 contention model, copy bandwidth bound or measured capacity. Kernel numeric/provisional opt-ins preserve failed strict fits and physical/deployment qualification false; duration availability must not be relabeled accuracy.

Host release uses `max(handler_start + not_before_offset, predecessor_completion + after_predecessors)` (`:54`–`:69`). `DagHostReleaseProvider` uses source-bound topology/issue-depth features and pooled family/task parameters. It does not read a future target node duration, measured release offset or measured handler endpoint (`dag_host_release_v5.py:232`–`:251`). The terminal tail is attached after predicted dependency completion, so a service prediction error changes handler completion. Natural handler duration cannot uniquely identify CPU launch supply; front-loaded and issue-depth schedules are members of a conditional feasibility set, not confidence bounds. OCR's synchronized native-call return is an upper bound on device completion, not an observed exact final-sync timestamp (`:90`–`:110`, `:200`–`:210`).

After every node completes, the lifecycle provider independently adds `parent_receipt_ms` and `worker_next_ready_ms`. `finish_ns` is parent receipt and owner availability follows worker ready (`cuda_dag_simulator_v4.py:103`–`:121`). One must not substitute handler end for E2E, parent receipt for next-ready, or infer either from kernel sums. Power and memory are conditional on handler-active owners, including host delays; board energy covers the measurement window, memory includes drain (`:172`–`:202`). This resource scoring is separate from request admission and from remaining resource work. Current bundle `resources=null` and `require_energy=false`, `require_memory=false` do not turn missing resource evidence into measured evidence.

The disconnected components have substantive implementations, not just names:

- `gsdeploy/forecasting/queue_diagnostics.py:18` and `:77` compute profile work, oldest waiting age, strict admission FIFO blocking, recovery episodes and empirical multi-scale envelopes. `gsdeploy/forecasting/simulator.py:170` instantiates it. The actual DAG engine never does. Normalized resource times milliseconds are not bytes, instructions, counters or a stability certificate; unknown demands stay unknown.
- `gsdeploy/runtime/batching.py:32` selects a same-owner/task/execution-key/length-bucket FIFO prefix, checks actual max length times batch size, and applies the head's absolute wait deadline. It reports padding and formation wait. `:95` invokes the exact backend batch once. `batch_owner.py:173` uses that selector in a real owner runtime. `batch_profiles.py:21` requires exact input/configuration profiles; no linear batching discount is assumed. This is complete-request batching. Oversized prefill requires a missing microbatch executor; continuous decode/preemption/KV migration are outside its scope. No target batch measurements are bound into this pilot.
- `gsdeploy/forecasting/observed_state.py:81`–`:124` uses reader receipt time for START/PHASE/HANDLER_END/WORKER_READY visibility. Its kernel cursor remains UNKNOWN unless separately observed (`:139`, `:343`–`:360`). The package simulator accepts validated `forecast_cursor`; the actual DAG API accepts only requests arriving at or after `now`, not active requests reconstructed from this observer.
- `gsdeploy/forecasting/recovery_risk.py:34` takes only current visible diagnostics and declared future envelopes. It rejects simulated future maxima as current-state evidence. The model is logistic gradient-boosted decision stumps, not Sinan's CNN. `forecasting/__main__.py:81` makes risk an optional separate output; it does not change utility, FIFO or rho. None of those calls occur in the pilot gate, and no pilot-bound real risk artifact is present in its bundle.

The minimum implementation order after the current source-verification window is:

1. Complete the current sealed predictions and independent four-candidate collection/evaluation. Report service, queue, E2E/P95 and ranking checks separately against the predeclared thresholds. Preserve failed results; source availability and eight-template CPU success do not substitute for this step.
2. Use that independent result to locate service/host/handoff error. Check equal-context scheduling, unconstrained intra-owner progress, independent copy service and partially identified host supply before adding queue sophistication. Any changed model requires a new source-bound version and fresh heldout evaluation; keep existing pilot outcomes heldout rather than fitting and re-reporting them as validation.
3. Connect remaining work, oldest age, FIFO convoy/HOL explanation, backlog/recovery episodes and empirical envelopes to the **actual DAG engine**. Define work units explicitly and avoid additive critical-path or batched-service claims. Add visibility-safe DAG checkpoint/resume with tested host/receipt/ready cutoffs and explicit UNKNOWN GPU progress. Then connect a frozen rolling forecast/correction policy and independently evaluate its drift correction. Adding more audit artifacts without this execution wiring does not close the gap.
4. Add the four-task multi-context adapter and separate gate using original source identities and the shared interfaces below. Require joint resource/startup/generation support and actual target readiness before a four-task forecast or four-task validation claim. Known trained content remains a separate scope from unseen-input generalization.
5. Connect batch formation only after the target backend and exact batch/length/resource profiles exist. Model serial preparation, wait, padding, owner blocking and whole-batch delivery, retaining all request identities. Add recovery-risk prediction only after obtaining visible training snapshots and disjoint delayed outcomes with holdout evaluation. Keep it separate from the original six utility terms and rho unless a new policy experiment explicitly changes them.
