Missing normalized resource demand remains unknown, and neither diagnostics nor adapters alter the six equal utility weights or the stability rule.

The standalone gate distinguishes two scopes. A training-template diagnostic requires an extra opt-in and every exact template once. A prospective forecast requires explicit exact-content generation support and its opt-in; a missing four-task descriptor remains UNKNOWN. Joint conditional resources need their own bound provider. Startup for a complete four-task executable flow is not yet qualified, so the result exposes active-window metrics and `deployment_utility=null`. It does not create or impersonate a prospective pilot seal. These limits must be closed before using this entry for four-task deployment utility or independent accuracy claims.

Caching must preserve the current v6 numerical contract. The integer-clock correction intentionally differs from the failed v4 run, so the comparison baseline is uncached v6, not v4. Do not round model durations, combine floating-point accumulations in a different order, reorder tied events, collapse resource transition records, cache request finishes across routing candidates, or infer GPU progress from host age. A lazy cache also preserves the first encountered UNKNOWN reason; eager evaluation of unused templates can change failure behavior.

Validation for a cache patch should compare uncached and cached v6 results on the same complete cohort, all four static routes and both predeclared host scenarios. Compare exact starts, handler ends, parent receipts, next-ready times, queue waits/depth samples, activity counts, resource windows/transitions, six score terms, UNKNOWN reasons and diagnostics, with timestamp/source-receipt metadata separated from numerical outputs. Assert independent mutable state between candidates. Repeat source, history-manifest, SQLite identity, byte metadata, provisional-opt-in, quality/lifecycle and mid-run mutation counterexamples; all must still reject. Instrument hashes, bytes read, JSON/SQLite parses, constructor calls and cache hits alongside elapsed time and peak memory. A cache speedup is established only after those counts and equivalent outputs are measured.

No cache strategy in this document changes or restarts the current sealed03 CPU producer. No new GPU workload, weights, counters, permissions, threshold relaxation, measured-target fallback or request dropping was used for this preparation.
