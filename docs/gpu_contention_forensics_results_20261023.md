# 分流负收益的细粒度证据：从请求耗时到共享执行

本次对已审计的401/402四份主策略原生记录及301/302受控校准作只读拆分，没有重跑GPU或修改冻结包。当前可以识别工作量变化、handler活动重叠和资源代理失配，尚不能定量认定SM、带宽、上下文切换各贡献多少。

## 1. 先分清工作量、独占速度与共跑状态

分流请求在G2的平均输出token为6.90/7.74，关闭分流时同输入专用为6.87/8.11，没有系统性生成更长答案。未分流且同family的2142个文本请求，其输入token、输出token、有效生成配置、终止原因、请求/协议身份及预测文本在on/off全部相同。跨模型tokenizer、提示和量化后端仍不同，不能仅由token相近认定FLOPs相同。

每个分流输入均匹配到301/302两个同驻留、同模型、同输入和生成工作量的独占活动参照。用bG/bS表示两个参照均值，hG/hS表示实际配对服务耗时，可严格记账：

`hG−hS = (bG−bS) + [(hG−bG)−(hS−bS)]`。

|平均耗时差|401|402|
|---|---:|---:|
|实际G2比专用服务多用|1101.469ms|1206.978ms|
|相同工作量独占参照G2−专用|−192.455ms|−252.854ms|
|两路径相对各自参照的残差差|+1293.923ms|+1459.832ms|

这些被选输入的G2独占参照反而较快，因此不能简单说“通用天生处理慢”。残差包含共享执行、host、同步、缓存、频率和跨轮迁移，不能全部称GPU竞争的因果代价。

同工作量受控条件还显示：G2与一份专用共跑时，其whole-handler服务/独占参考均值为1.994（64匹配）；与两份专用共跑时为2.659（63/64匹配，排除一次输出长度不同）。专用在SS条件为1.509，在SSG为1.962，各128匹配。共跑双方都可能变慢，但这些是有限批次handler比，不是每个kernel的减速或自然持续负载下的物理上界。

## 2. G2执行期间真实发生了什么

用worker的`end_ns−service_ms`到`end_ns`重建service区间，再按每个worker真实开始/结束切分；不是按host pending数猜正在GPU执行。分段总和闭合，G2同worker任务无服务重叠。此仍是host handler活动时间线，不是CUDA kernel trace。

|分流子组|401|402|
|---|---:|---:|
|全部G2文本服务时间中，两专用同时活动的占比|69.04%|65.87%|
|E2E更快子组的相应占比|38.61%|0.39%|
|E2E更慢子组的相应占比|76.45%|78.81%|
|更快子组：G2未完成前新启动专用请求的均数|1.00|0.50|
|更慢子组：对应新启动数|5.25|6.56|

这比“后面有新到达”更具体：后续请求确实不断在专用副本上进入服务，G2可能长时间处于变化的共跑环境。较慢请求本来就更容易遇到后续启动和重叠，所以上表不能识别因果方向或据此估算固定干扰比例。

一个同轮同输入的对照更有针对性：402中pool后缀`67471c73406819007dce75ed`在G2均为4007输入token、5输出token，但：

|请求|G2服务耗时|服务期间后续专用启动数|双专用共活动占比|
|---|---:|---:|---:|
|measurement:613|657.307ms|0|0%|
|measurement:483|3977.516ms|7|51.97%|

这是相同G2工作量在不同执行环境中约6倍的时长差，值得对其启动顺序和设备时间线作受控复现；不是相同初态下的随机干预。其他同输入好/坏重复见取证CSV。

## 3. 不只是G2变慢：专用也付出服务代价

与G2文本服务时间重叠的专用请求，相对关闭分流时同请求的service平均增加：401约56.157ms（122请求）、402约27.600ms（79请求）。新统计使用以service_ms重建的区间口径，因此402与此前用wrapper范围计出的80条略有不同；重建起点可能含wrapper尾部的小量偏移，不是直接记录的service计时起点。

进一步仅保留两轮alias不变的请求，并按相同输入和alias分层，重叠组相对不重叠组的“配对service变化”加权差为62.626ms和17.939ms。这减少了输入和副本变化的部分混杂，仍不能消除系统状态、热态和重叠时长选择效应，不能当成因果干扰系数。

服务代价不等于净延迟：某些专用请求虽然service增加，但等待下降更多，最终更快。所有未分流文本合起来的平均E2E仍分别增加13.442ms、35.679ms，不能只挑共跑或受益子组替代全系统评价。

## 4. 漏未来到达与模型太粗是两个独立问题

沿实际已发生的共享活动状态，用冻结进度系数积分得到模型计入的等效进度W（单位为独占服务毫秒），再除以相同输入经验独占基线b。W/b是模型一致性诊断，不是FLOPs、token实际工作量或因果干扰比例。理想的经验模型应使W/b靠近1；这个比值大并非任务真的计算了更多token，而是该模型沿真实轨迹计出了过多进展。

|G2文本子组|401 W/b均值|402 W/b均值|
|---|---:|---:|
|全部有支持上下文的分流|2.211|2.139|
|更快分流|1.152|0.982|
|更慢分流|3.137|3.584|

各轮有一条OCR重叠请求因缺已校准上下文保留UNKNOWN，G2可评价30/31和18/19。没有补零或epsilon。

因此，即使事后已知后续开始/结束，坏例仍无法由原family-count速率模型解释。仅给旧模型加未来到达模拟还不够，需要改共享执行模型的状态粒度和适用域。

专用的重建比在有上下文支持的子集中，on约0.890/0.894（1001/1086、1006/1056），off约0.903/0.899（1036/1117、1023/1075）；与G2重叠的有支持专用约0.766/0.779。旧模型对G2进度偏乐观的同时，对一些专用共跑进度可能偏保守。这提示模型间不对称失配，尚未证明是设备调度偏向或某种特定硬件瓶颈。

## 5. 不能漏掉GPU之外的服务开销

源码核查表明service_ms包括infer中的准备、拷贝、generate、CPU结果处理，以及出口同步、cache reclamation和再次同步。入口同步在service计时之前；worker_latency还含外层工作。

401文本请求中768/1117实际执行cache reclamation，其中G2为20/31。`empty_cache`位于service计时内，但现有记录没有其分项耗时。超出同输入同工作量受控最大service的G2请求为16/31、8/19；这些慢例没有更集中于回收发生或更长输入，因此不能据回收频繁就认定是主因，也不能未经显存验证关闭回收。

当前内存采样是容量，功率采样是整板watts；两者都不能告诉我们显存带宽、SM占用或context切换时间。独立worker进程已证，MPS及实际多context调度未知。没有TTFT/逐token时间，不能分解prefill与decode。

## 6. 下一步应当围绕机制做小实验

先保持当前模型驻留和同输入，分别比较G独占活动、SS、SSG单批、SSG持续异步换入、SSG受控启动准入；随机化顺序、重复并保留无profiler基线。在关键差异出现后，交叉控制输入混合、持续供给与启动相位，避免一次改变多个因素后归错因。

使用新隔离源码的阶段标记和Nsight Systems关联request、CUDA API、kernel与CPU事件，回答：

1. G2是kernel本身执行变慢，还是提交后等待执行更久？API到kernel开始还含stream依赖，不能直接全算context调度。
2. 变慢集中在prefill、decode，还是同步、分配/回收和CPU供给？NVTX是host范围，需关联实际设备活动。
3. 有可用硬件计数器时，是否存在同shape/阶段下的SM或DRAM/L2证据？同kernel名不等于同工作量；NCU replay会扰动并发，不能拿其耗时当自然竞争事实。
4. 限制后续专用启动是否减少G2长尾，代价是否小于新增的专用等待？同一到达cohort全部计账，不能暂停任务却不算等待。

详细可执行合同与判别标准见[机制验证协议](gpu_contention_mechanism_protocol_20261023.md)。本次未采集GPU kernel trace，当前环境GPU管理工具不可用，未尝试绕过。已装profiler版本也尚未验证设备/计数器兼容性。

## 7. 对算法的具体含义

下一版不能只扩展预测长度。应先验证带输入工作量、执行阶段、同卡其他模型阶段、持续供给及残余进展的条件减速模型；给G2和专用分别建模，不预设对称。按识别到的机制选择动作：路由、待启动并发准入或host/缓存热路径优化。

决策的核心账应包含“当前请求等待节省−自身额外处理−其他请求外部代价”，再按原完整U加入质量、截止完成、显存与能耗。输入与阶段预测只能用决策时可得信息，不能把本次事后重建轨迹倒灌在线。

若机制实验表明持续供给下无法取得足够净处理能力，正确的算法应拒绝这类分流；若能通过阶段配对或启动控制保留局部收益，则以具备同样调度能力的自身禁分流控制检验系统净收益。局部kernel解释、预测变准和最终总效用正收益需要分别验证。
