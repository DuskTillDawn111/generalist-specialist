# 闭环诊断之后：两档开放负载的条件式门禁草案

日期：2026-10-22。本文只检查已有协议与冻结源码，未读取本批实际 run.json、live、queue 或原生输出，未运行 GPU。`analyze.py`、`plot.py`、冻结 packet、预测器与评分均未改动。本文件不是已绑定实验协议，也没有给出新的负载数值或通过判定。

## 1. 这六次诊断能决定什么

固定驻留 `text×2 + generalist_2×1 + ocr×1`，A/B/C 分别仅专用活动、仅 G2 活动、三者活动。每个活动 alias 都收到完整32输入×3轮，两块独立启动。它们能发现同输入服务变化、原生输出变化、跨块漂移、部分共同活动及资源问题。三状态不是连续负载实验；它们不识别 `service(rate,share,background)` 的函数，也不给出开放负载最大稳定吞吐。

下一步的目标应是**选两档风险受控的开发测量负载**，用六个开放条件收集新证据，而不是由闭环结果宣布负载已验证。区分三个结论：

- `GO_CPU_SCREEN`：身份与诊断足以做有限 CPU 情景筛选。
- `GO_OPENLOOP_DEVELOPMENT`：明确限定域、未知项、风险留量和停止条件后，可以进入新的开发测量；不意味着容量或预测器验证通过。
- `GO_FORMAL_SEARCH`：新预测器冻结后通过独立开放负载验证，六项预测及约束均有证据；本批诊断不能直接产生此结论。

若没有可信候选区间，结论为 `STOP_NO_SUPPORTED_LOAD_INTERVAL`，不能用“先跑六点再说”替代门禁。

## 2. 在读取本批终态后先做的检查

依赖全部六次终态收据与 SHA 的独立分析；所有块同时入账，不能选较快块、较好轮次或较好输出。先形成下表，缺项为 UNKNOWN，不由其他项代替。

| 检查 | 判据草案 | 未满足时 |
|---|---|---|
| 身份与完整性 | packet/worker/READY/路径/输入/时间账本通过；各活动 alias 96/96，32输入各3次；无非法同 alias 重叠或单在途违反 | 停止该上下文迁移，定位身份或执行问题；不填补服务 |
| 资源与测量 | 每块真实内存合法、无外来进程、能量覆盖/进程退出完整；资源与能量独立审计分列 | 不把 completed 当 eligible；资源失败状态不能进入可行候选 |
| 跨块重复性 | 同 state/alias/input 的中位服务比、handler 比、token 与输出变化分开报告；同输入三轮漂移和时间四分段一致检查 | 整体尺度漂移或输入相关变化超出预声明容差则 STOP，不把两块平均拟合 |
| 共同活动覆盖 | C 的每个 alias、每个输入、每块都核对“所有活动 alias 同时忙”的请求次数与 handler 暴露比例；同时报告某 alias 结束后的尾段 | 覆盖不足则 C 不能代表持续共同活动；不从少量重叠片段拟合共同活动容量 |
| 原生质量 | 每请求原生成功/输出可评分；同输入重复输出及 EM/F1 变化；成功和质量不是同一个字段 | 缺失/失败保留 UNKNOWN；系统变化使离线输出复用假设待验证，不能改历史分数 |
| 背景证据 | G2/image、G2/asr、OCR/ocr 的完整输入身份与服务/输出证据核对；并声明其与 text 联合活动仍未测 | 缺路径先补具体覆盖，不能由21条priming或 H600 的约6条背景请求证明对应完整输入池路径 |

重复性可使用 `z_i=log(median_service_block2_i/median_service_block1_i)` 的整池中位偏移、绝对偏移的高分位及超阈输入数；同时列出各输入，不把192条重复请求视作192个独立输入。三次重复只能用于描述，不能构造可靠高置信容量上界。生成长度差可帮助解释变化，不能事后删掉“长输出”请求或将实际生成长度变成未来预测特征。

这里的容差记作 `epsilon_block`、`epsilon_drift`，最低共同活动请求数/暴露比例记作 `m_common`、`gamma_common`。**若本批原协议未冻结这些数值，不能读完结果后制定恰好通过的门槛再称本批验证通过。**本批只能生成开发问题清单；新数值必须在下一批相关测量之前冻结，必要时用新诊断检验。单纯“有一次正 overlap”不等于充分覆盖；B 单 alias 的 all-active 指标是平凡条件。

如果跨块差大，先检查已记录的执行身份、priming/warmup、温度/频率/限频、输出token、CPU/IPC账本与资源。找不到稳定状态则停止确定性容量迁移；选择重复更强、分状态的不确定性模型需要新协议，不能用两个状态的平均值隐藏变化。如果 C 覆盖差，下一次应是另行声明的均衡、持续共同活动诊断（相同输入分布、驻留与有限超时、明确覆盖门槛），而不是盲升开放到达率以追求 overlap。

## 3. rho、整池服务、整池质量与正式质量的四个口径

### rho 的数学约束不改

冻结 `config.validate_plan` 为每族计算：

`rho_m = sum_t(r_tm * S_pool(m,t,n,context) / 1000) / capacity_factor(m,n)`。

在现有 per-input replay 契约中，`S_pool` 是完整固定输入池的逐输入服务中位数的**等权算术均值**，不是中位数的总体中位数，不是正式 SWRR 分给该族子集的均值，也不是 `1/closed_loop_rps`。副本效应已在 n 对应的 per-worker baseline 中时，不能再次乘/除 n；继续按冻结 `capacity_factor` 和现有缩放实现核对。

`rho<=0.8` 必须保持。它是当前模型下的必要配置门禁，并不证明真实运行稳定。新增的开发安全余量只能额外收紧选点，不能重定义原约束。旧迁移模型已经失败，不能因为旧 `validate_plan` 返回通过便声称新上下文容量可信；UNKNOWN 不是零负载或可行，也不能把新的诊断表直接注册为 validated service 绕过门禁。

### 固定全池质量保持原画像值

每模型/任务的全池历史 EM、accuracy、CER、WER 作为固定画像与对照保留，不因哪个路由赢、哪个块较好而重估。诊断整池原生输出可以检验复现性，但仍是开发观测，不能悄悄替换冻结质量记录。专用高于通用是原画像事实/设计条件，不是必须维持的硬准入阈值。

同分布假设下 `Q_pool_proxy = sum_t alpha_t * sum_m p_tm * loss_pool_tm` 可作为**单列的机制检查**，用于观察通用分流的整池平均质量代价；它不是正式实际 Q。

### 正式 Q 使用精确输入暴露

正式 `predict_quality` 用固定 task 输入池、指定 seed 的 shuffle、每任务连续游标和运行时 alias-expanded SWRR，逐次查询该输入被分给的族的历史输出。正式 `measure_quality` 对实际完整 measurement cohort 的原生输出评分。两者用固定到达率任务权重；text/image 按错误请求，OCR/ASR 按总编辑错误/总参考字符或词数，不能平均逐输入 CER/WER，也不能按完成请求重选任务权重。失败/缺失不能得0损失。

即使全池画像质量固定，**SWRR 的候选 Q 仍可随路由、有限窗口请求数和 seed 的输入映射变化**。这是原合同下的有限轨迹暴露效应，不是模型精度突然改变。不能用“保持质量固定”为由把正式 Q 强制换成全池份额加权常数；若以后要改变输入编排/评价目标，应另立版本并同步预测、执行、MILP、DFS和验证，本批不做。

## 4. 正式 SWRR 输入子集：CPU 上必须先输出完整 roster

沿用正式 H600、arrival process、warmup30、原排空/评分与输入池。正式测量的 SamplePool 和 Router 从各自新状态开始，不能让 priming/warmup消耗测量游标。每档负载、份额0/1/8/1/4、每个预声明开发 seed，均用冻结 `make_trace -> SamplePool.next(task) -> expand_routes/Router.choose(task)` 顺序重建，存 trace SHA、完整 scheduled rows、task_position、pool_id、family、alias 及每输入计数。

不能用理想分数的分母/LCM代替实际 SWRR：浮点累加和 tie 规则使有限序列未必有理想周期；只对重建的有限序列报告实测周期。原半分流就出现族各16/32、alias仅9/32且多数集中8输入的情形；提高 H 或换负载不会自动解除这种对齐。

每条件报告：

1. 整任务/族/alias的 offered 覆盖、每输入重复数、相互交集，以及预测 Q 与直接逐输入累积 Q 的逐任务一致性。
2. 按同 alias/同输入比较的服务情景；不能将不同路由各自不同输入均值直接解释成干扰因果效应。
3. formal-input-cohort Q 与全池代理 Q 的差值，但只有前者进入原正式预测。不能挑 Q 更有利的 seed，不能择优轮换起始游标，不能换路由来“修好”原生质量。
4. `.01 rps × H600` 的背景小样本全量列出；它验证的是当前有限正式 cohort，不能覆盖整个任务池，也不证明长期混合工作负载。

新开发 seed 先核对未占用后冻结，81/82继续留独立验证、71–73留最终确认，旧61/62不复活为新独立验证。不要因为某 seed 让两模型输入更均衡或 Q 更好便更换声明。

## 5. 两档负载的可执行 CPU 选点规则（不在本文硬定数值）

先限定候选域：固定 n2 驻留，背景 image/asr/ocr 各 `.01 rps`，路由分别 G2/G2/OCR；目标 text 的 G2份额 `s in {0,1/8,1/4}`，专用两 alias 等分余量。只生成有限的 text 到达率网格 `Lambda_dev`，以及两档额外风险留量 `eta_L < eta_H < 0.8`、最小可分辨负载间距 `delta_lambda`、FIFO积压/排空风险阈值和情景枚举规则。这些写入下一批 CPU 选择声明，在启动新 GPU 之前冻结。

### 5.1 服务情景，不拟合连续耦合

A/B/C 的完整输入、alias、块、重复观测保持分层。可以构造多个离散**观察情景**：按块/alias保留全输入服务向量，再做逐输入较慢值等预声明压力情景，用于拒绝明显风险；不能挑快状态。观察最大值仅是已观测情景包络，不是概率上界，更不是所有开放负载/混合背景的上界。共同活动覆盖不足的 C 不可被当作联合活动情景。不得从A/B/C三个点回归连续share/rate函数，再把未测点称作模型验证域。

必须另列 G2/image、G2/asr、OCR/ocr 的已核对路径服务情景和背景联合活动未知。text-only C不能证明G2的text与image/asr多任务共排队。原始 standalone/per-input 基线可作为注明来源的风险情景；旧失败迁移倍率不重新成为可信模型。若没有可解释的保守服务情景或遗漏重要路径，停止选负载。

### 5.2 每个 lambda×share 同时过两种筛选

- **全池工作量筛选**：每个情景按整池均值与原 capacity_factor 计算各族 rho；同时披露现有正式 `validate_plan` 的结果与模型身份。新情景的安全检查单列为 `diagnostic_rho_scenario`，不能伪装成生产认证。若有独立验证且适用的新模型，则其原正式 rho门禁也必须通过；没有则候选仍仅是开发风险点。
- **精确有限轨迹 FIFO 风险筛选**：用每个正式计划请求的已知 input/alias、到达时间和对应情景 per-input service，模拟每 alias共享FIFO及G2多任务顺序；从 scheduled 起算延迟，不能从 actual submit 起算隐藏 host积压。报告窗口完成率、队尾、尾段增长、预计排空和所有 UNKNOWN；任何实际 service oracle 都不能用于选将来的负载。这个回放同样只是一组情景，不是新状态的正确预测证书。

定义 `F_eta(lambda)` 为三种份额在全部已声明情景下均满足 `rho<=eta`、资源已知合法、有限轨迹风险阈值且无关键 UNKNOWN 的集合判据。只对**共同可比较的三路由**选择：较低档从 `F_etaL` 中按预声明确定性规则选一个，较高档从 `F_etaH` 中选择严格更高且间距足够的一点。可采用“低档为共同区间内部代表点，高档为共同可支持区间中较高点”的固定网格索引规则；不得按预测 U 最大、目标结构胜出或事后实际结果选 lambda。未声明的数值和网格应在终态诊断结论明确后另封选择包，而非在本草案中虚构。

较高档是**较高开发压力点**，不能称“接近最大稳定容量”。若零分流不在共同集合而分流在集合中，不能偷偷删除零分流来维持六条件方案；停止本轮“可行方案间效用改善”的选点，另议并标记容量救援/可行性改善研究。若只有一档或两档差异无法分辨，也停止，不为凑两档强行外推。

## 6. 下一批执行与停止，而不是自动升级

CPU选择收据至少含：输入/source SHA、允许的lambda网格、seed、三路由、正式trace及input roster、所有服务情景来源/缺口、rho两口径、FIFO风险表、选择规则和被拒原因。包中要明确 `diagnostic_only/unvalidated` 的模型状态，不生成新的validated performance profile。正式原生测量沿用既有合法执行/评分入口；如旧门禁因模型缺失而拒绝，不改规则绕过，应先建立明确的开发测量契约或解决模型证据缺口。

先执行低档三路由开发条件，全部保留后检查原稳定性重构和补充机制指标，再决定高档是否仍可执行；应在完整六条件包预先写明“低档失败就暂停高档”的停止规则。停止不触发自动重试，也不在已完成结果中另选较低/较好替代点。若修改负载/状态/规则，另建新版本并保留原失败。

停止理由包括：资源失败、UNKNOWN/身份错误、native质量不完整、正式 cohort 偏离、低档仍有持续 host/worker积压或服务/输出状态改变、背景联合任务引发未建模漂移、风险情景明显低估、新阈值未预声明。原正式稳定性允许 `recoverable_congested` 获效用资格，但它不等同长期稳定；下一步模型/更高档选点应继续检查到达窗口的计划积压、已提交积压、尾增长、完成比例及排空依赖，不能只看最终全部完成或原eligible。

低档通过也不自动验证高档，H600通过不自动验证H1800。六个开放开发条件仅可用于开发，之后冻结预测公式/参数/域/误差/排序分辨标准，再用新独立seed做完整背景下的配对验证。发现没有可可靠识别的分流收益区间或目标结构，应报告未识别，不强行拟合、改质量、加压或扩池来得到预期答案。

## 7. 当前建议的最小下一动作

1. 主对话在六次终态后运行既有独立分析与审计，填写第2节事实表，不把未冻结的容差当既定通过标准。
2. 只用 metadata 扩展正式输入暴露审计，使任意候选lambda/seed/三路由都输出精确roster和frozen Q；不用运行raw，也不用GPU。
3. 根据明确的缺口决定是停止/补具体路径或共同活动诊断，还是封一个有限CPU情景筛选包。只有输出两档共同候选且边界明确时，才准备新的六条件开放开发包。
