# BO–MADS 有限预算调度改进：实现、对照与接入

2026-11-05。本次已修正“尚有激活组合未探索时 EI 一直得不到执行”的调度问题，并将新调度接入通用 v3 入口。只新增预先限定的 **6 次 CPU 搜索**，复用六份旧结果；六次最终效用均提高。96 项相关测试通过，192 次内层返回通过独立枚举检查。

本轮使用上一阶段相同的 7/14 模型合成排队成本场景，**不是全 7 个真实模型的验证**。没有新增 GPU 实验、重训、改变效用或扩展真实预测器范围。

## 实际修改

新增[预算调度器](../gsdeploy/continuous/budget_scheduled_bilevel.py)，继承原优化器的 GP、MADS 风格轮询、部署池和渐进 MILP，保留原控制器源码用于复现。

1. **定期让全局搜索执行。** 初始化结束后先给全局搜索一次机会；默认每经过最多四次非全局路由评价，就再次让出执行机会。它仍受时间、预测和 MILP 的共同预算约束。
2. **EI 与激活探索交替。** GP 有认证数据且拟合成功时，前两个全局机会用于 EI，第三个保留给新激活集合；没有可探索集合则回到 EI。没有有效 GP 时继续探索，不使用未认证值伪造训练样本。
3. **重复精化有总量与单路由限制。** 最多占初始化后剩余路由预算的 25%，同一路由最多两次。此次四次初始化后剩 28 次，因此重复精化最多七次；初始化、所有新路由、精化仍统一计费。
4. **局部搜索及时交还调度权。** 默认每批最多尝试一个新的 MADS 候选；已有认证结果直接复用，不重复收取路由评价次数。被配额延后的部分结果保留原上下界与未认证状态。
5. **过滤已经能证明无法部署的提案。** 仅当 oracle 明确提供完整、非负、有效的可加显存下界时，才根据活跃模型所需的最少显存跳过超限候选。缺失证据时不裁剪，不把单独运行的显存估计套到未知共驻场景。

这些改动整体比较，不把全部效用改善归因于单一配额参数。调度报告记录全局机会、精化次数、延后原因与显存过滤次数；过滤次数包含反复生成的候选，不代表独立部署个数。

## 预算和对照如何保持公平

[预定协议](../configs/bilevel_scheduler_improvement_20261105.json)固定 7/14 模型、种子 11/29/47、总计六次新搜索，不搜索调度参数。每次仍为 60 秒、64 次预测、32 次路由评价、128 次 MILP 调用。

复用上一阶段相同的四个计费初始化及精确内层，逐条核对分流比例、值、上下界、认证和工作计数一致。问题身份与 oracle 版本也相同。原来的连续参考区间直接复用，不重跑参考求解器。新结果的每条内层返回仍由独立有限部署枚举核查。

发布条件在运行前固定：两种规模的最终效用中位数都不得下降，预算与认证检查通过，EI 在具备条件时实际执行；否则保留旧默认。结果满足条件，故接入新默认。没有因结果进行第二轮调参或补跑。

## 六次完整结果

U 越大越好；“提高”是新 U 减旧 U，未将负效用换算成含混的百分比。

|模型数|种子|旧 U|新 U|提高|EI 次数：旧→新|预测次数：旧→新|
|---|---:|---:|---:|---:|---:|---:|
|7|11|−0.380109937|−0.377305615|0.002804321|0→8|36→39|
|7|29|−0.383480257|−0.380109937|0.003370320|0→9|38→39|
|7|47|−0.383683332|−0.380109937|0.003573395|0→8|34→39|
|14|11|−0.380109937|−0.379667977|0.000441959|0→9|49→53|
|14|29|−0.380109937|−0.379195224|0.000914713|0→7|50→53|
|14|47|−0.383683332|−0.380109937|0.003573395|0→8|48→53|

7 模型最终 U 中位数由 −0.383480257 提高至 −0.380109937；14 模型由 −0.380109937 提高至 −0.379667977。六次都用完 32 次路由评价，重复精化均为七次，没有突破总预算。

**本次改善的是相同预算上限下的方案质量，不是更少计算。** 实际预测比旧版多 1—5 次。新运行的 CPU 时间约为 0.396—0.624 秒，旧记录约为 0.162—0.296 秒；旧结果来自不同批次，不用这些时间做严格速度比。EI 打分和候选过滤增加了搜索开销。

## EI 确实参与了方案改善

14 模型种子 11、29 的 EI 提案各直接产生一次更好的已知方案，分别增加效用约 0.000442、0.000915。两次选中的 text→共享 specialist 比例约为 **14.1104% 和 20.3406%**，其余 text 交给 text specialist；image 交给共享 specialist。它们不在四分之一比例网格上。

7 模型胜者仍在四分之一网格上，不能因此宣布连续精修在所有规模都占优。此次没有在新调度下补跑单分支消融，也没有证明 BO–MADS 普遍优于 MADS-only。已有证据足以说明“EI 被调度挤出预算”的问题已被修正，并在两个 14 模型运行中产生实际收益。

六次结果仍与参考最优存在差距：7 模型约 0.001207—0.004012，14 模型约 0.007261—0.008176。保留激活空间上限与启发式选点，不声称连续全局最优或经典 MADS 收敛证明。

## 已接入的使用入口

[通用 v3 入口](../experiments/solve_bilevel_v3.py)现在默认使用 `balanced`：

```bash
python experiments/solve_bilevel_v3.py \
  --config configs/paper_fifo_reference_v2_cpu_fixture.json \
  --output /path/to/new-output-directory \
  --scheduler balanced --method BO-MADS \
  --seconds 300 --predictions 64 --routes 32 --milp-calls 128
```

`--scheduler legacy` 可显式使用原调度。Python 的 `solve(..., scheduler='balanced')` 也支持该开关。以上示例是已有 CPU fixture，不是实际硬件配置；本次无需再次运行。

原 `ActivationAwareBilevelOptimizer`、此前真实范围搜索入口和历史实验脚本保持原行为。直接使用库的新调度时，导入 `gsdeploy.continuous.budget_scheduled_bilevel.BudgetScheduledBilevelOptimizer`。这避免原始对照随默认实现更新而悄然改变。

本次修改了通用 v3 入口，旧版文件已在修改前保存快照与 SHA256；历史报告不改写，旧验收的入口源码身份对应旧快照。目标效用和真实预测范围没有变化，新入口的实现身份会自然更新以隔离缓存。
