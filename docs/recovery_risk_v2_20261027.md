# Optional delayed-backlog risk predictor

The main queue predictor remains the event simulator. The optional `gsdeploy.forecasting.recovery_risk` module implements a separate, frozen classifier for delayed queue buildup or slow recovery, inspired by [Sinan, ASPLOS 2021](https://doi.org/10.1145/3445814.3446693) and its separation of short-term latency prediction and longer-term risk. Sinan studies CPU microservices; its measured accuracy and architecture do not transfer automatically to this GPU deployment. This module does not replace queue execution, alter FIFO, change original stability/rho acceptance, add a seventh utility term, or reject requests.

## Feature contract and connection to diagnostics

`build_features(...)` accepts the current decision time, execution-context SHA, visible queue work in solo-profile milliseconds, oldest waiting age, observed HOL blocked time, waiting count, the visible-state observation time, the public workload declaration time, and future multiscale work envelopes. Future sources must explicitly be `declared_schedule` or `sampled_declared_workload_scenario`. Envelope rows are `{window_ns, max_offered_solo_work_ms}` in increasing scale order; their work must come from public input costs and the declared future planning scenario. Missing resource/input costs remain UNKNOWN. Work is profile work, not measured GPU instructions or a deterministic arrival/service bound.

Queue diagnostics can supply the units and calculations, but use the **current visible snapshot** for current queue work/age/HOL. The simulator's maxima over its future horizon are not current observed features. Use its declared-workload scenario envelopes separately. A feature envelope carries schema `gsdeploy.visible_recovery_risk_features.v2`, `clock=host_perf_counter_ns`, execution identity, current `observed_at_ns`, `visible_state_time_ns`, and `declared_at_ns`. The current envelope must be assembled for the decision time, with the underlying state/declaration no later than that time. Extra label/outcome fields, device/Unix clocks, actual validation arrivals as the purported public scenario, future timestamps, and missing work are rejected. The source declaration is an explicit provenance contract; the module cannot prove that an externally mislabeled array was not drawn from future measurements.

`RecoveryRiskProvider(model, execution_context_sha256, allow_cpu_fixture=False).predict(features, now_ns)` returns a risk model score and target definition, or raises `UnknownEvidence` for unsupported features/scales. Optional CLI integration can attach this to diagnostics from `risk_request={model, features}`. No training occurs in the prediction path. The score is not applied to six-term U or admission decisions.

## Offline labels, freezing, and separation

`fit_recovery_risk(training_rows, context, horizon_ns=..., recovery_threshold_ms=...)` consumes explicit training rows. Every row supplies unique id, run id, group id, split, physical/CPU kind, execution SHA, decision time, the feature envelope available at that time, and a separate offline outcome. Outcome fields are `window_start_ns`, `window_end_ns`, `observed_until_ns`, `violation`, and `recovery_ms`. The binary target is a violation in the predeclared subsequent horizon **or** observed queue recovery exceeding the configured threshold. Full-window and recovery observations are required: censored outcomes cannot silently become negative labels. A row's outcome is never an input feature.

Training requires at least three runs, at least two groups, and at least two examples of each label class. Runs/groups are explicit split units such as independently collected workload runs and their related experiment families. They must be assigned before evaluation; these strings do not themselves establish statistical independence. Validation rows are rejected by the fitting API. The model binds the execution SHA, label horizon/threshold, feature scales, training ids/runs/groups, class counts, per-feature training support, and a complete JSON ensemble under a SHA-256 identity. Physical measurements and CPU fixtures cannot be mixed, and CPU fixtures require the explicit opt-in on loading.

The environment has numpy/scipy but does not have sklearn installed. The implementation therefore uses a small numpy logistic gradient-boosted decision-stump ensemble with squared negative-gradient fits and bounded shrinkage. This is an explicit shallow boosting adaptation, not a reproduction of Sinan's CNN or its complete training procedure. The serialized model contains only numeric trees and metadata; it does not use pickle or execute serialized code. The provider checks the frozen model hash again at prediction time to reject accidental in-place modifications.

Prediction requires exactly the trained feature scales and values within each feature's observed training range. Unsupported ranges return UNKNOWN rather than extrapolating to an apparently precise overload forecast. This per-feature envelope is a minimal support check; it does not establish joint distribution support, calibration, or robustness to workload drift. Such evidence requires larger independent profiles and tests.

## Evaluation and limitations

`evaluate_holdout(provider, rows)` accepts validation rows only and rejects any id, run or group overlapping training. It requires both label classes and returns count, held-out run/group identities, accuracy/balanced accuracy at score 0.5, and ranking AUC. This API cannot fit or update the model. The 0.5 threshold is an evaluation convention, not an execution rejection rule. Results explicitly state that scores are uncalibrated, confidence intervals are absent, and physical risk accuracy is not established.

`tests/test_recovery_risk_v2.py` uses synthetic separable run/group fixtures to exercise the held-out evaluation path, frozen JSON reload, long-recovery labels, one-class rejection, censored-label rejection, run/group leakage rejection, future-feature rejection, missing/out-of-support UNKNOWN, and invariance of existing forecast/score values. The synthetic ranking result verifies the implementation path only. No GPU data was collected, no real risk accuracy was measured, and no long-term recovery benefit is claimed.

The next empirical requirement is a prospectively split collection containing actual buildup/recovery episodes and both target classes under the new execution backend. The current model deliberately does not claim that a few successful synthetic tests validate GPU overload recovery.
