# ASR 高负载分流：容量、显存与强对照预筛

结论：ASR=2.6 rps、QA/image/OCR 各 0.05 rps 是优先开发点，2.5 用于检查网格敏感性，2.7 用于检查容量边缘。**必须保留 ASR×2+G2×2 这个强替代**，不能只与不分流或 ASR 三副本比较。现有画像支持候选定位，尚不支持新负载下的已验证效用或物理可行性结论。

## 方法与证据范围

输入是未修改的 `surrogate-v2/system-config.json`，函数来自未修改的 `execution-source-v5`。读取七模型全部画像、副本行和逐输入记录。原 workload 下先通过 `validated_replay_spec`，计算每条路径的 `replay_path_statistics.mean_ms`；新 rates 只用于独立必要容量算术，**没有把新负载送入旧 VALIDATED 门禁，也没有改 spec/workload/hash 来绕过门禁**。

对 ASR 2.5/2.6/2.7，背景任务 text（QA）、image、ocr 各 0.05，容量条件为每家族 `sum(q_mt*service_seconds_mt)/capacity_factor_mn <= 0.8`。小规模 LP 仅最大化可分流 ASR 总速率，保持三个背景流守恒，不计算效用、排队尾部或 GPU 同卡干扰。全任务禁分流则枚举任务到家族的完整分配。缺失画像路径不补值。

只用约 1.6 秒 CPU 完成 131250 个原 count vector 的显存算术，548 个非空配置通过显存必要筛查；没有完整 FIFO 预测、长搜索、GPU 或模型执行。原始配置和冻结数学源码 SHA 前后相同。可复核脚本与完整 JSON 位于 `artifacts/static-study-gpu-20261022/spillover-capacity-controls/`。

显存以正式 `replay_auxiliary` 对**原未改 workload**返回的 `safe_memory_mib` 为准：`max(safe_factor*sum(memory_table)*memory_multiplier, training_deployment_memory)`。其中 safe_factor=1.110854、memory_multiplier=1.2216725559481743、预算=49140 MiB。所有下表部署均与正式函数逐项交叉核对。该 calibrated 显存是预测约束，不是实测硬件界；不能将 standalone safe memory 或实际 NVML 值与它混为一谈。

| ASR×2+G2×1+OCR×1 | 40248.9 | 2.79256 | 2.74182 | 主候选，text/image→G2、OCR→专用 |

| ASR×2+G2×1+G3×1 | 49132.4 | 2.70362 | 2.63006 | 仅余 7.6 MiB 预测预算，不能先删；多通用竞争结构 |

| ASR×2+text×1+image×1+OCR×1 | 51947.1 | 1.87862 | 1.87862 | 纯专两副本也超预测预算 |

K8 是**分母 1..8 的并集**，不是只允许八等分。表中连续列允许三个背景任务也连续分流，是必要容量上界；K8 列只允许背景整路由、ASR 网格分流。后者对多通用配置不是完整 K8 路由域的最优证书，不得用其低值排除全部背景分流。所有“上限”均针对现有画像的 rho 模型，不是新的物理吞吐观测。

另有 ASR×2+G2×1+OCR×{2,3,4}，以及 ASR×1+G2×2+OCR×{2,3,4}，通过必要筛查；前一族 OCR×4 的显存为 49108.0 MiB。它们容量相同但副本画像、延迟和显存不同，不能为了固定目标结构提前裁掉。全部 11 个连续容量至少 2.5 的部署保存在 JSON 中。

## 不分流、纯通及三专用副本的独立排除边界

ASR 专用 n=1/2/3 的无背景 q08 分别是 1.17310、1.87862、1.96420 rps；n=4 为 1.97339，但单独正式预测显存已经 51548.1 MiB。n=3 单独显存 38661.1 MiB，能驻留但不覆盖 QA/image/OCR；加入最省 G2 也达到 50182.8 MiB。**“ASR3 单独显存可行”不能转换成“ASR3 纯专全任务可行”。**

所有显存可行 count vector 中，全任务整路由的最高 ASR 必要容量为 **1.87862** rps（例如 ASR×2，背景交给通用/OCR）。因此 2.5/2.6/2.7 下，最佳不分流在当前模型中都应报告容量不可行，保留域与原因。不能为得到一个可测数值，降低它的 offered workload、放宽 rho 或改为丢请求；也不能只凭它失败，就宣称主候选效用优于所有组合。

独立 LP 同时检查全部显存可行纯通配置，允许不同通用家族间 ASR 和背景都分流。其最高必要容量仅 **1.85864** rps，来自 G2×1+G3×3，显存 47031.7 MiB：背景全部在 G2，ASR 可分 G2 0.42771、G3 1.43093。常见的 G2×2+G3×2 为 46716.8 MiB，但受背景服务影响上限只有 1.57270；G3×4+OCR×1 为 50299.5 MiB，超预算。G2×3+OCR×1 虽只用 37518.4 MiB，上限也仅 1.52094。以上没有漏掉原 n 行，缺失服务路径继续未知；结果仍是必要容量模型筛查，不是实际纯通硬件失败记录。

## 网格与余量

ASR×2+G2×1+OCR×1 用 ASR 2/3、G2 1/3 时：

| ASR offered rps | ASR×2 rho | G2×1 rho |
|---|---:|---:|
| 2.5 | 0.70974 | 0.73266 |
| 2.6 | 0.73813 | 0.76051 |
| 2.7 | 0.76652 | 0.78835 |

2.7 的 G2 距 0.8 已近，最应观察开放到达排队、服务膨胀和 drain。ASR×2+G2×2 同为 2/3 对 1/3，三点 G2 rho 分别为 0.73982/0.75766/0.77551；更高副本数并不自动意味着更差容量，必须作为竞争者测量。

ASR×1+G2×2+OCR×1 在 2.5 rps 用 **专用 5/11、通用 6/11**，rho 分别 0.77495/0.76982，满足现有连续条件；这个路由包含在 K16 而不在 K8。因此 2.5 点必须增加 K16 同域敏感性或显式标记只是 K8 证书。2.6 主点不依赖这个离散化排除，因为该部署连续上限已经低于 2.6。

## 下一批 GPU 开发点建议

先声明新负载研究合同、输入/参考池、原六项权重、延迟参考、显存预算和 rho 规则；原画像及正式确认数据保持冻结。以下是**建议开发点，尚未在本次执行**，可采用相同 seed42、300 秒正式窗口、30 秒 priming、300 秒 drain，先做 4 组上限；短窗口是开发测量，不能替代 1800 秒独立确认：

1. 2.6，ASR×2+G2×1+OCR×1，ASR 2/3→专用、1/3→G2；建立目标混合路径及新负载响应。
2. 2.6，ASR×2+G2×2，同样 ASR 2/3 对 1/3、全部背景→G2；直接测最有必要的多副本强替代。
3. 2.5，ASR×1+G2×2+OCR×1，专用 5/11、G2 6/11；验证 K8 排除是否只是网格问题。
4. 2.7，第一组部署及路由；检查最紧张的 G2 占用、排队和资源稳定性。

只有第 1/2 组通过完整能量、质量、cohort 和稳定门禁后再继续；失败按原原因保留，不因目标结构未出现而改质量/负载。若尚有预算，优先补 2.6 的 ASR×2+G2×1+G3×1 或同主部署的不同 ASR 分流比例，而非测已经确定违反必要显存的纯专三副本配置。近预算配置必须先作实际资源 preflight，预测余量小不能算物理余量。

这四组用于开发与暴露错误，不足以直接验证新负载预测器。后续需在预声明的新 workload 条件上完成独立 heldout 验证，再对全部七模型、原副本行、共同 K 和同一六项效用做自由搜索、最强其他部署/路由、禁 ASR 分流、全任务不分流及纯角色比较；预算结果保留 gap/未知域，不将容量 LP 当效用搜索。

## 独立验收标准

- 新预测器/新负载验证必须与开发点分离；旧 spec 的 workload 校验不得放宽，正式 seeds43/44/45 不参与开发调参。
- 只有自由搜索在完整声明域中主动选中 ASR 专用至少两副本，且 `0<ASR→G2 rate<offered`，才支持“多专用副本仍向通用分流”的结构结论；不能事先固定该部署再称主动选择。
- 必须报告 ASR×2+G2×2、2.5 的 5/11 强替代、其他通用组合、三专用/纯通的覆盖与不可行原因；将 no-split 容量失败与可行竞争者的效用差分开。
- 所有实测使用同点同负载、共同输入/种子/时长/priming/drain、同板卡能量与原质量评分，保留 routing conservation、实际请求路由、实测资源与 queue 指标。不能降低对照负载或把失败请求从分母移除。
- 结构与效用都需独立确认；未完整或未认证保留状态。静态最优分流只证明预先选择的固定路由比例；若要声称依据实时排队主动转移任务，还需另行定义并测量在线调度策略。
