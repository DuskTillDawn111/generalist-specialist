# 五项静态效用评价规范（草案 v2）

本规范对应 2026-10-14 确定的五项等权方案：吞吐、平均延迟、显存、尾延迟、能耗各 0.2；质量为硬准入条件，不参与加权。它是待实现的评价定义。当前代码仍实现四项旧效用（T/L/P/M=0.25/0.30/0.30/0.15），没有能耗采样和五项总效用；本次仅写文档，没有改公式或运行 GPU 实验。

**1. 评价对象与比较条件**

评价完整部署和路由方案 `(x, r)`：`x_m` 是模型 m 的副本数，`r_tm` 是任务 t 分给模型 m 的请求率。没有强制保留通用或专用模型的约束。一个模型是否值得加入，取决于整个方案的变化。

同一对照必须固定任务集合、输入池、任务请求率、到达轨迹/种子、GPU、预算、测量窗口和归一化参考值。参考值与权重在比较候选方案之前冻结，不能根据结果改动，也不能给各候选方案设置不同分母。

|符号|含义|单位|
|---|---|---|
|lambda_t|任务 t 的固定输入请求率|请求/秒|
|Lambda|所有任务请求率之和|请求/秒|
|alpha_t=lambda_t/Lambda|任务 t 的流量权重，和为 1|无量纲|
|H|计划正式测量窗口长度|秒|
|N_off|完整计划到达轨迹中，落在 `[start,end)` 的请求数|请求|
|N_done|上述 cohort 在有界排空结束前完成的请求数|请求|
|N_win|上述 cohort 在正式窗口结束前完成的请求数|请求|
|d_ti|请求 i 的端到端延迟|毫秒|
|b_t|任务 t 固定的参考延迟|毫秒|
|B|固定 GPU 显存预算|MiB|
|f|显存安全系数，当前约 1.110854|无量纲|
|P_ref|固定能耗归一化参考功率|W|
|A|部署启动成本的统一摊销服务时长|秒|

零需求任务不进入本次评分。正需求任务缺少观测不能填零延迟或零损失。预热/priming 请求不进入正式请求指标；正式 cohort 的排空完成请求保留在延迟和完成率中。

**2. 总效用与权重**

```text
weights = {T: 0.2, L: 0.2, M: 0.2, P: 0.2, E: 0.2}
Q_weight = 0  # quality is an admission gate

U = -0.2*T_loss -0.2*L_norm -0.2*M_norm -0.2*P_norm -0.2*E_norm
```

五项统一写成成本/损失，越小越好，所以 U 越大越好，合法完整评分一般不大于 0。负号不是失败标记。五项权重之和为 1；不能给质量再加 0.2，否则变成六项。

“等权”仅表示归一化后每增加一个单位的惩罚系数相同，不保证实际影响相同。当前参考比值式 L/P 可大于 1；包含一次性成本的 E 也可大于 1。暂不自动截断或按候选集合 min-max 缩放，以免丢掉严重退化或使候选池扩展改变旧方案分数。后续如引入明确 SLO 的有界满意度，应另立版本并重做对照。

**3. 吞吐项：完成了多少输入需求**

先保留原始计数与速率：

```text
completion_ratio = N_done / N_off
offered_QPS      = N_off / H
within_QPS       = N_win / H
T_loss           = 1 - min(1, within_QPS / offered_QPS)
                 = 1 - N_win / N_off
```

范围 `[0,1]`：全部在窗口内完成时为 0，窗口内只完成 90% 时为 0.1。有界排空能够证明 cohort 最终完成，却不能抹去窗口内吞吐损失。运行提前终止时仍使用完整计划窗口及轨迹，不能使用实际短运行时长或仅已提交请求重新做分母。

当前代码还计算 `1-min(1,N_done/N_off,N_win/(Lambda*H))`。本稿建议五项版本统一使用冻结到达轨迹的 N_off，解决低流量/有限窗口中 `N_off != Lambda*H` 导致的供给计数惩罚；落地时需同时更新预测器和离线评估。它不解决缺少某任务延迟观测的问题，后者需增加预测覆盖或延长实测窗口。

本项评价当前输入负载下实现的吞吐，不奖励部署后的空闲最大容量。剩余容量和压力上限另行报告。完成请求也不等于输出正确，输出质量由质量准入和质量诊断记录评价。

**4. 平均延迟项：一般请求要等待多久**

端到端延迟定义：

```text
d_ti = (host_completion_time_ns - scheduled_arrival_time_ns) / 1e6
mean_t = average(d_ti for all completed formal-cohort requests of task t)
L_norm = sum_t alpha_t * mean_t / b_t
```

计入主机调度迟到、发送与输入处理、worker 排队、模型推理和结果返回。不能只拿 GPU kernel 或 worker handler 时间替代端到端延迟。排空阶段完成的正式请求继续参与计算。

归一化含义：任务平均延迟等于参考值时，该任务比值为 1；是参考值一半时为 0.5；两倍时为 2。再按输入流量占比加权，不用完成请求比例重算 alpha。它评价平均请求体验，适合反映常规处理速度和队列等待。

当前参考值如下，沿用原静态配置，未重新标定：

|任务|b_t（ms）|
|---|---:|
|Text|10.0263802667|
|Image|27.7167365111|
|OCR|11.8801065222|
|ASR|574.4954926167|
|LID|76.2558906944|
|Visual QA|160.1164576111|

这些是历史归一化基准，不是用户声明的 SLO，也不是某候选方案自己的延迟。预测与实测必须使用相同 b_t。零流量任务可以不使用其参考值；正流量参考值必须有限且大于 0。

**5. 尾延迟项：较慢请求的体验**

```text
p95_t = percentile_95(d_ti for task t)
P_norm = sum_t alpha_t * p95_t / b_t
```

保留完整请求延迟集合，按项目当前的线性插值样本百分位计算；正式 cohort 的排空完成请求也在集合中。P95 是经验分位，不表示一次短实验已认证长期 95% 延迟。

本项评价排队突发、慢输入、共享模型任务阻塞等尾部代价。它使用与平均延迟相同的历史参考值 b_t；当前没有独立 P95/SLO 参考表。归一化同样不截断，P_norm 可以大于 1。

这里是“各任务 P95 的流量加权平均”，不等于“把所有任务请求合并后求全局 P95”。全局 P95 单独报告，不能冒充 P_norm。每任务同时保存请求数、P50/P95/P99、均值和原始延迟，稀疏任务分位只作有限样本描述。

**6. 显存项：部署持续占据多少资源**

规划沿用已有实测副本表：

```text
M_plan_safe = f * sum_m memory_table[m][x_m]
M_norm     = M_plan_safe / B
```

副本数量查实测表，不假设 n 个副本的容量或显存均为单副本的 n 倍。一个副本服务多个任务，只计算一次驻留显存。

实测沿用当前驻留成本口径：

```text
M_run_safe = f * max(owned_memory_after_warmup,
                    owned_memory_after_measurement)
M_norm    = M_run_safe / B
```

内存按本次运行拥有的 worker 进程求和，包含模型和驻留缓存等占用。预算 B 当前为 49140 MiB。有效方案的 M_norm 在 `[0,1]` 内，0.4 表示安全修正后的驻留量占预算 40%。

运行中采样峰值另作资源合法性检查，不拿它与驻留快照混称同一指标。采样峰值也不等于不可观测的瞬时峰值。超预算或有干扰进程时，不能仅扣一点显存分数继续排名。没有真实显存观测时，只能报告规划代理。

本项体现 GPU 内存空间的占用和机会成本，不等于 GPU 计算忙碌程度或耗电。

**7. 能耗项：完整方案的用电成本**

第一版计入单张 GPU 整卡能耗；CPU、内存和整机能耗尚无统一测量，不声称已包含。方案独占目标 GPU，整卡功率包含基础空闲耗电、模型驻留及推理期间耗电，不减掉空闲基线作为主评分。

运行期能耗：

```text
J_run = integral(power_draw_w(t), t in [measurement_start, measurement_end])
```

采样积分可以用梯形法。功率必须带与测量窗口对齐的时间戳，并覆盖窗口边界；不能外推缺失区间或将采样失败填成 0。W = J/s；结果以 J 保存，换算 Wh 为 `J/3600`。该值是功率遥测积分估计，需要保留采样间隔和硬件测量范围。

一次性部署能耗单独记录：

```text
J_once = J_load + J_priming + J_warmup
P_effective = J_run/H + J_once/A
E_norm      = P_effective/P_ref
```

三个一次性区间彼此不重叠，也不与正式测量区间重叠。A 是所有候选共享的预期部署服务时长。默认 `A=H` 表示本次启动后只服务一个测量窗口，等价于 `(J_run+J_once)/(P_ref*H)`；长期部署比较应事先指定更长 A，防止把短验收的启动成本误当成长期每秒成本。

`P_ref` 取实验预先冻结的参考功率，例如固定 GPU 的功率上限。历史 RTX 4090 记录为 450 W，仅用于解释格式；正式对照应冻结其目标 GPU 的实际配置，不在此运行新采样。若 H=A=120 秒、P_ref=450 W，则参考能量为 54000 J。

E_norm=0.3 表示计入摊销启动成本后的有效平均功率为参考功率的 30%。它不同于每请求能耗 `J_run/N_done`：每请求能耗另行诊断，避免少完成或丢弃请求时误导总成本。E_norm 包含一次性项时可超过 1，参考值不是能耗硬预算，也不做自动裁剪。

新增模型的能耗不一定上升：专用可能接走昂贵通用推理而降低整卡总能耗。不能简单相加各模型独立运行的电量或为每个新增模型虚构固定能耗。显存 M 评价空间占用，E 评价实际能源成本，两者有不同含义。

**8. 质量、覆盖和稳定性的硬条件**

质量按模型—任务路径判定，记录模型/检查点身份、质量指标、数据集和协议。accuracy/exact match 等达到业务下限，WER 等不超过业务上限。不能只因为模型是通用就放行，也不能为了得到某种部署结构修改阈值。LID/VQA 等旧记录尚无完整数值门槛，需要补充业务质量政策。质量达标后的额外改善暂不加权，原始分数继续保存。

部署还必须满足：全部正需求任务被覆盖、路由流量守恒、只使用有记录的副本数、显存预算有效，以及当前 rho<=0.8 的规划边界。代表任务容量转移是代理，需要保存不确定性。

正式实测 U 还要求：原生模型运行正常完成、没有错误或未完成 cohort、稳定性规则通过、质量证据通过、显存与能耗证据完整。可恢复拥塞只有原稳定性规则确认恢复后才可计入。仅“排空后全部完成”不能单独证明稳定。

**9. 缺失数据、诊断与预测**

缺能耗、某任务缺延迟、质量缺证据、运行失败或不稳定时，完整五项 `U=null`、`eligible=false`。保存已知的原始指标和分项；不填 0、不重新分配缺失项权重、不把四项结果叫作五项总效用。若 J_once 未测，完整本版 E 也未知；稳态 J_run 可以单独报告，不能无标记地代替含启动摊销的 E。

预测与实测采用同一公式和参考参数，证据等级分别标注。预测能耗必须来自有适用范围的测量/模型；未知部署和路由不能默认无成本。能耗可能依赖整个同卡组合，旧优化器的局部可加性与剪枝不能自动延用，必须验证新的能耗模型和搜索方法。若只覆盖部分候选，不能声称整个域的最优。

**10. 如何评价新增模型或副本的正负效用**

对固定输入，比较合法方案 A 与新增模型/副本并重新路由后的 B：

```text
Delta_U = U_B - U_A
        = 0.2*(T_A-T_B)
        + 0.2*(L_A-L_B)
        + 0.2*(P_A-P_B)
        - 0.2*(M_B-M_A)
        - 0.2*(E_B-E_A)
```

正收益可以来自吞吐损失、平均延迟、尾延迟或能耗下降；负收益可以来自延迟恶化、显存增加或能耗增加。任何一项都可能因完整路由变化而反向，不预设专用永远有益或新增副本必定线性增容。原方案不可行时，报告可行性恢复，不把缺失/非法 U 当成 0 计算 Delta。

以下是说明公式的假设数值，不是实验数据：

|项|A：原方案|B：新增模型后|Delta_U 分项|
|---|---:|---:|---:|
|T_loss|0|0|0|
|L_norm|1.0|0.7|+0.06|
|P_norm|1.5|1.0|+0.10|
|M_norm|0.4|0.5|-0.02|
|E_norm|0.3|0.4|-0.02|
|总 U|-0.64|-0.52|+0.12|

更高显存和能耗被性能收益抵消，所以 B 更好。Delta>0 是算术改善；是否可信还需匹配输入、完整证据和独立重复。不能把一次短验收的小正数当作已确认的部署收益。

**11. 每次评分必须留下的记录**

保存 `weights`、`config`、任务请求率与 alpha、到达轨迹/输入池身份、H/A、全部归一化参考值、部署和路由、质量证据、计数/速率、各任务延迟集合与样本数、驻留显存与峰值、功率时间序列和分阶段 J、五项归一化值、五项贡献、U/eligible/reasons、稳定性以及证据适用范围。报告同时展示原始单位和归一化分项，不能只给一个总分。
