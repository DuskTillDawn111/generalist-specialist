# 持续共同活动诊断建议：primary + bounded support

日期：2026-10-22。仅CPU设计建议；未改当前run、packet、评分和预测器，不启动新GPU。依据本批全部终态及 `joint-service-diagnostic-v1` 的分阶段证据，当前建议是**暂停到达率/容量外推，先补持续共同活动识别**。独立审计v2 PASS证明记录/身份/资源/能量检查通过，不证明闭环共驻模型或开放负载稳定边界通过。

## 现有证据与需要修正的统计解释

固定 n2 驻留下，两块 C 的最后专用handler约86.60/87.77秒结束，G2整体约125.92/126.91秒完成；B仅48.47/47.33秒。C G2首轮服务均值2935/2960ms，而后两轮约492–501ms。G2 96请求中正共同活动仅18/14条，分别只覆盖18/14个输入各一次；零共同活动78/82条。同输入同轮C/B服务比的正共同活动组中位9.486/11.252，零共同活动组0.999/1.007。这里分组是事后描述，不是验收阈值或因果处理组。

最关键的是：两块各32个输入的三次服务中位数，**32/32全部来自专用结束后的纯尾段**。每输入至少有两次尾段观测，因此三次中位数抹去了该输入最多一次的共同活动慢段；总体中位数也接近B。整段算术均值能够揭示总服务工作量显著增加，所以不能笼统说“均值漏掉变化”；真正会掩盖机制的是混相位总体中位数、三次输入中位数及不分相位的平均解释。完整时序/分数散点必须与统计表并列。

最长请求为block1 G2 sequence10，service17.439秒，配对B约1.367秒，C/B12.759；prediction及24个生成token相同。block2最长15.034秒，生成24token和配对输出也相同。每块96配对中94个prediction、94个generated_tokens相同；共同正overlap组分别17/18、13/14相同。token/输出差异不能解释全部慢段，但也没有因果证据把慢段归给GPU争用、缓存或温度。cache_reclamation只含performed及unused-reserved前后MiB，没有独立耗时，不能把内层service全部或任意一段归为cache成本。

## 建议协议的核心

保持 `text#0、text#1、generalist_2#0` 为活动alias，OCR继续驻留；固定模型、副本、输入池、解码、priming、设备、safe_factor和memory预算，不加入正式image/asr/ocr流量。本次仅识别text持续联合活动这个窄上下文，后续完整背景还需单独验证。

每alias预声明96条**primary**请求：相同32输入×3轮、每轮完整打乱，映射与seed均冻结。primary是本次主要输入覆盖队列，不是独立96输入。central release，所有活动alias同时开始，每alias至多一条在途。

某alias完成自身第96条primary后，不能退出活动状态；从其独立、预声明的**support**游标继续发同池请求，每alias仍只有一条在途，直到全部活动alias的primary均完成。support序列不消耗其他alias或primary游标，不动态选择难/快输入，不使用答案或待测服务。可采用单独命名空间seed按完整池循环打乱，顺序在启动前可完全重建，冻结最多1024条support/alias。若G2先完成，则G2也必须发support；因此规则对所有活动alias对称，不能只硬编码“专用补padding”。

结束条件是最后一条primary获得终态成功响应；停止新support admission，记录确切primary目标完成边界，再有界排空已经在途的support。primary窗口与support排空分别记录。不能把support响应当primary请求、不能以support完成补齐缺失primary，不能将任意成功响应算作原生质量完整。

## 边界与失败必须预先写入packet

- 整个测量阶段硬wall600秒、每请求300秒；两者先到先触发停止。wall界包含测量期primary与support活动，结束/排空阶段也须明确独立绝对截止；不能因support使总等待无界。启动、warmup、shutdown继续沿冻结有界协议。
- 每alias support最多1024条（不含96primary和独立warmup）；若primary未全部结束却有alias support耗尽，立即停止新admission并将本次诊断判coverage失败，不能让该alias闲置后继续声称持续joint，也不能自动加上限/重试。
- 保留所有primary预注册记录；未发出、在途未完成、失败均保持不同status和UNKNOWN时刻，不能补造service。所有已release support全量保留，含request_id、独立support_sequence、pool_id、alias、实际时刻、输出、质量可评分性、cache、tokens和失败。
- 任一资源/进程/内存/原生请求错误按原监测停止；每条attempt终态都保留，不自动重试。测量结束时仍在途support不能被静默丢弃，若排空失败则完整状态按预声明规则失败。
- 必须重新实测安全显存峰值、整卡能量覆盖、所有resident进程与无外来进程；当前n2历史余量不是持续活动下的安全保证。不能把support使用量加进正式效用分母、产量或质量权重。

## 验收与解释应在执行前冻结

至少两个新开发block，每次fresh workers，保持全resident最大输入priming与30秒warmup。新seed先核对未占用，81/82和71–73继续保留。是否另做B对照、如何平衡顺序及所需运行总数，应在新包中明确；本建议没有自动安排额外GPU。已有B只能作为历史开发参照，新协议与执行状态改变不能自动认为B完全可迁移。

逐primary请求计算实际handler与所有活动alias handler的连续交叠比例，报告每alias/每输入/每轮完整分布。前后边界跨越、dispatcher补发间隙、每次stdout/IPC间隔均真实保留。每alias“总是在循环请求”不等于每个handler100%同时忙，不能从admission逻辑推定实际overlap。

执行前冻结最低共同活动覆盖（每输入/每轮需要多少有效primary及交叠比例）、跨block同输入服务变化容差、时间漂移、输出复现、原生成功与资源门槛。`>0`、`>.95`、`>.99`等本批事后描述切分不能直接继承为“已验证阈值”。如果primary仍有输入只在弱overlap时出现或跨block差大，结论是持续joint证据不足；不能把缺口平均掉再拟合。

support的角色是维持活动上下文，不增加独立样本量；primary按32输入聚类，support单独列请求量/时间/覆盖/资源。support还可提供描述性漂移观察，但任何用其拟合的下一模型必须明确开发数据身份、输入依赖与新验证范围，不允许声称1024条支持请求带来1024个独立验证样本。

## 相比增加固定cohort或副本数

把所有alias固定96直接增成192/更大，完成时间仍大致按自身速率分离；快alias仍可能先结束，慢alias后两轮又变成单方尾段，不能保证各输入获得持续joint观察，且无谓增加双方请求数。对称bounded support以“全部primary结束”为联动条件，直接针对这个缺口，通常比统一放大固定请求数更有效；它依然不能保证实测交叠比例与成功覆盖，必须按事实验收并允许失败。

增加模型副本n会改变资源、调度和研究上下文，已有text n3资源超限，不能用其代替n2持续joint识别。support保持部署不变，只延长活动，便于区分原先混合尾段的统计问题；但时间延长可能带来温度/频率/缓存状态改变，因此仍非因果实验。

如果持续joint下G2的96primary需超过600秒，正确结果就是有界失败/不足，不能由本批尾段快服务推断它一定能完成。即使新批成功，也只支持这个固定部署的text joint情景；不承诺容量、不自动解锁两档open-loop、不拟合share/rate连续函数。下一步仍须补背景联合路径、在明确CPU风险情景下选择开发负载，并另做独立开放负载验证。
