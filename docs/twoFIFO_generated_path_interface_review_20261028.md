# New-schema generated-path interface review

This is a CPU source review, not a new fit, generated experiment or qualification.
The useful numerical core exists, but the old law and generation orchestrators
cannot consume the new data unchanged. Two simulator limitations need an isolated
new version: owner-specific rates and continuation from a nonempty actual history.

## What “phase12” means

The fixed `own_family_phase_count_global_same` design has **11 family:phase
categories plus one shared same-phase slope**, hence 12 coefficients. It is not
12 semantic phases. Text replicas share the text category; G2 has its own entry,
prefill, decode and READY tail; OCR has entry, inference and READY tail.

The fitted response-coordinate rate is `exp(-beta · vector(owner, phase, state))`.
The existing rate helper supplies an explicit rational approximation. The
simulator must query `(owner, semantic_phase, n, same)` at each generated visible
state, where `same` compares the original semantic phase strings. Prefixing phase
names with owner/family to squeeze them into v4's three-key table changes the
meaning of `same` and is not a valid adapter. The old heterogeneous simulator has
the four-key rate interface but releases a worker after parent READY processing;
it cannot replace the actual two-FIFO engine.

For a donor macro, integrated fitted rate converts its observed response and
each internal mark to reference-work coordinates. That is training compilation.
For a target request, those jointly chosen coordinates run against newly
generated peer states. Target actual START, macro clocks, future shapes, stop
length, query outcomes, peer paths and notice times cannot enter the prediction
compiler. Donor whole-request templates for exact public input remain an explicit
template-transfer assumption, not a general generation-length predictor.

## Minimum new interfaces

1. `fit_new_blocks(intake, features)` returns full/fold fits with block IDs,
   source receipts, immutable feature design and qualification certificates.
   Pure fit math is reused. Only complete three-block intake enables this path.
2. `build_joint_law_v2(training_documents, qualified_fit)` returns complete
   request vectors and provenance separately. It compiles all measured messages
   using a whole-attempt decomposition that includes priming history; priming
   does not become measured response-fit labels. It has no old baseline fit
   dependency merely to obtain notice slacks.
3. `compile_draw_v2(joint_vector, public_key_ordinal, transport_support)` returns
   immutable request plan, per-mark three-station slacks and a complete explicit
   transport draw, or an UNKNOWN reason. No historical request/case/offset ID is
   a lookup key. The plan has zero dispatch delay because transport is separate.
4. `simulate_twoFIFO_v5(public_calendar, plans, owner_phase_rates,
   protocol_slacks, transport_draws, initial_state, case_windows)` generates
   sender/worker/protocol state continuously. This is a small extension of the
   established equations, but restoring nonempty state is a real engine change,
   not a schema-only wrapper around `v4.simulate`.
5. `evaluate_block_ensembles_v2(...)` holds out all four shards in one block,
   generates every offered request and scores at each original case 10s+60s
   cutoff. Unknown/incomplete worlds retain the full request/world denominator.
   One shared finite donor draw scheme is fixed in advance; no candidate/seed
   selection from heldout error. Heldout request IDs align evaluation only.

## Sampling and dependence

The highest-level donor latent is one of the **training blocks**, with equal
block weight. Four startup attempts inside a block are not four additional
replicates. Source attempt/raw/request IDs remain provenance. Within that block,
the public `(owner, task, exact input)` and arrival ordinal identify the draw
slot; a complete request vector is selected jointly. Every entry/forward/OCR/tail
work coordinate, mark, query outcome, READY and paired notification-slack vector
moves together. Sampling per macro or per lag independently destroys the
observed dependence. The ordinal is public-key arrival ordinal, not overall
owner ordinal or completion/dispatch order.

Using one common block latent across inputs preserves only block-level
dependence. Independently sampling request vectors conditional on that latent
does not preserve all source attempt/cross-request correlations; this must remain
an explicit empirical-law assumption. A source-order attempt bundle can preserve
more dependence only when its selection uses declared public conditions and its
work/notice coordinates are regenerated; donor absolute peer/START trajectories
still cannot be replayed. Source-derived transport constraints and any explicit
latent transport scenario must stay paired with the originating request vector.
No invented probability mass turns an unidentified latent split into a fitted law.

## Initial history, producers and fixed windows

At a forecast cutoff, `case_histories[].prior_history_snapshot` is the past
observation boundary. Inspect availability before using body fields. Its
`request_records`, `queued_runtime_events`, READY roster and source clocks must
be mapped explicitly. `pending_request_ids` is the runtime record registry and
is not by itself a list of unfinished handlers. Do not derive initial state from
the final raw's future-completed version of a prior request. If a past handler
has not delivered READY by cutoff, its remaining work/release is latent and must
be conditioned/generated rather than copied from its later actual READY.

The required continuation state includes per-owner sender release/queue,
worker active macro and virtual age/release, visible processed phases, pending
reader/collector/RESULT messages, station clocks, source producer sequence and
phase/issuance watermarks. One stdout producer persists per owner for the whole
attempt; distinct owners have distinct producers. It resets only at a real new
worker startup. READY from one request may still be in the parent pipeline when
the next request starts. Reinitializing per request or per case erases this fact.

`v4` currently requires empty initial pending messages and does not restore
active/visible/producer state; its returned fields are not a complete checkpoint.
Two honest modes are possible: continuous generation after a source-bound
initialized attempt (including generated priming), or conditional forecasting
from an explicit nonempty cutoff state. The latter is the immediate match for
the captured actual-prior-history requirement. Missing initial components return
UNKNOWN. Zero timestamps are allowed only for a demonstrated fresh/empty
boundary or a deliberately labeled supplied synthetic scenario.

Generating priming from startup additionally needs explicit supported priming
templates/transport for all eighteen inputs/tasks; excluding priming from the
response-fit labels does not automatically supply that law. An actual observed
pre-case history can support a conditional cutoff mode without claiming that
startup and priming were themselves predicted.

The collector dynamically chooses case epochs after checkpoint work. For
within-case conditional evaluation, that chosen public epoch is known at the
case origin and all future relative arrivals are the frozen plan. Predicting an
entire startup-to-final-case calendar requires an explicit law/supplied scenario
for inter-case orchestration gaps; do not silently treat future observed epochs
as a prospective scheduler. Keep each measurement interval 10s and its drain
60s. A combined long interval including gaps is not the original measurement
score. Attempt startup/priming occurs once, not once per case; its energy and
peak are separate from case measurement energy and through-drain memory.

## Unknowns and claim boundaries

Actual busy rows show worker queueing and parent clock behavior, but do not
separately identify complete-stdin-line availability and next-handler pre-START
continuation. The five-field `TransportDraw` must be explicitly complete. A
conditional sensitivity ensemble may use clearly supplied feasible latent
scenarios; its probabilities and changed-schedule transport are unqualified.
If no supported transport draw is available, keep the world UNKNOWN and retain
the denominator. Neither total observed submit→START nor a zero-filled draw is
a scientific busy-transport predictor.

`numeric.fit` fits response-wall association conditional on processed evidence.
Static projection proxies, phase count slopes and sample board-resource tables
do not identify physical SM/DRAM/L2 demand or prove cache reuse. Full/fold
numerical certificates, generated timing errors, independent validation,
resource accuracy, ΔU ordering and final diversion benefit are separate gates.
No part of this interface review qualifies any of them.
