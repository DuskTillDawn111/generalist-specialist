2.7rps的另一强竞争者为text n3、专用份额3/4，诊断分数−1.000983，比n2/50%低约.033733；其text rho .794743已经接近.8边界，且更占显存。n2专用份额2/3分数−.974358，仅比n2/50%低.007108，覆盖32个输入／路径，可作为未来开发时的邻近路由候选；本轮不据此添加任何GPU任务。

**对“不分流”的结论需要单独说明。** 逐输入池均值下text n3不分流rho=.8对应约2.0384rps；从2.1起本轮n3不分流均超约束，n1/n2不分流也不能解决这些高负载。故2.7的混合分流相对这些不分流结构属于容量救援情境，不能当作双方都可行时的分流效用证据。2.1–2.5虽也需要分流，但单副本加G2仍胜过双副本；“需要混合”不自动推出“需要两个专用副本”。

text1/2/3+G2n1+OCR1的原始安全驻留代理分别22265.96/32683.55/43101.14MiB，均在49140MiB预算内；真实共驻峰值未知。全部108个候选的功率特征至少一项超出旧训练范围，旧功率回归不能验证新负载。实际GPU计算竞争、带宽、温度、输出变化及尾延迟均没有建模，当前正差可能被这些影响消除。仅有一个固定开发种子，未筛选种子或修改精度以获得目标结构。

建议把2.7rps作为“若需要继续text方向时”的有限后备开发条件，优先比较n2/50%、n1/50%和n3/75%，并保留n2/2/3邻近路由；当前text1.8准备包保持未排队，此CPU结果不触发自动改包或GPU执行。
