# 分流负收益：GPU竞争机制的分层诊断与验证合同

目标是解释当前驻留下分流的等待收益为何被处理与后效应抵消，再决定算法应该观测和控制什么。宏观效用、handler重叠、CUDA kernel活动和硬件瓶颈是不同层次，不能由上一层直接推定下一层。

本文件记录新诊断设计，不修改已完成的五项实验、不改变权重或稳定性规则、不启动GPU任务。当前环境的`/usr/bin/nvidia-smi`是零字节且不可执行；Nsight Systems 2025.6.3、Nsight Compute 2021.3.1可返回版本，尚未验证GPU访问、计数器权限或版本与设备的兼容性。工具存在不表示已经有kernel证据。

## 可加的延迟账本

每个请求先按现有时间戳分解：到达至提交、worker等待、handler服务、handler外围、返回收集与时钟残差。请求及任务加权均值可加，P95等分位数不可这样分摊。

按相同输入分别取得G2和专用的独占服务参照bG、bS，在参照身份及生成工作量匹配时，可写严格代数恒等式：

`hG − hS = (bG − bS) + [(hG − bG) − (hS − bS)]`。

第一项是两模型独占参照差；第二项是实际运行相对各自独占参照的差中之差。它包括共享执行、host供给、同步、缓存、时钟和参照迁移等影响，不能直接命名为“GPU干扰的因果贡献”。独占仅两轮的噪声及匹配缺失须保留。

进一步检查同一family、相同输入、相同输出token与协议，避免将输出变长当作竞争减速。跨模型tokenizer、提示和生成设置不同，token数与service/token不能直接作为跨模型GPU效率指标。没有首token或逐token时间时，不能从总service反推出prefill与decode各占多少。

## 从当前记录重建到什么程度

用每个worker的`end_ns-service_ms`到`end_ns`重建服务区间，沿所有开始与结束事件切分，得到G2执行时text活动数0/1/2、OCR活动和背景任务的时长分布。相同worker的任务串行，G2图像/ASR不能与G2文本handler同时执行，但可以等待；两份专用则可能与G2并行。

Unix时间戳用于跨worker对齐，不能直接混用perf时钟；同一alias的区间须无重叠，每个请求分段之和须还原其服务时长。图中显示的是host handler活动，而非GPU kernel同时执行。一次CUDA调用可能异步，handler区间也包括CPU、等待和同步。

需要同时记录后续到达和后续真实handler启动：后续到达并不等于已经抢占GPU。比较好/坏分流的活动时长分布、持续换入新专用请求次数、混合输入与同输入差异，以及G2结束后的队列恢复情况。按实际完成定义好坏或后续到达会有选择效应，描述不能直接解释为因果。

已有受控校准的相对进度系数可以沿真实分段积分，得到模型计入的等效进度（单位为独占服务毫秒），再与相同输入经验独占基线比较；它不是FLOPs、token实际工作量或因果干扰比例。若模型累计计入的进度远超基线而请求才完成，说明仅按模型活动数的代理不足。该事后诊断使用真实已发生轨迹，不能回填早先在线决策，也不能将残差都归为算力或带宽竞争。

## 必须用profiling区分的机制

|候选机制|需要的联合证据|不能单凭什么判断|
|---|---|---|
|GPU执行位置/上下文等待|CUDA API提交、GPU kernel实际开始、设备调度/上下文记录；按进程和请求关联|handler区间重叠、worker队列为空|
|算力/SM资源竞争|同阶段同kernel的时长、SM/Tensor活动及并行排布，独占/共跑配对|GPU utilization接近100%|
|显存带宽/缓存竞争|同阶段同kernel的DRAM吞吐、内存停顿和L2等可用计数器，以及完成工作量|显存容量占用高或board power高|
|CPU供给/同步/拷贝|tokenize/prepare/postprocess范围、CUDA API、memcpy、CPU线程调度与GPU空洞|把整个service视为GPU计算|
|prefill与decode干扰|请求与阶段NVTX、首token/逐步时间、kernel关联、输入及输出长度|总service除生成token数|
|频率/功率/热限制|设备时钟、温度、功率限制状态与上述时间线，交错重复|长请求更慢或平均功率变化|

多进程存在不等于已证明CUDA contexts如何调度。MPS状态、实际kernel重叠及计数器可用性需要在新运行开始时记录。不能事先断言使用MPS一定更快或将MPS开关作为无对照的修复。

## 最小受控实验：先改变竞争模式，再追原因

所有模型保持当前驻留，保持输入、精度、生成规则、CPU线程与设备设置；先在开发样本中声明少量短/长工作量代表，不能按结果选正收益样本充当确认。每个目标输入运行以下条件，随机化条件顺序并分块重复：

|条件|G2目标请求|两个专用的实际执行模式|回答的问题|
|---|---|---|---|
|G独占活动|同一目标|驻留但无请求执行|同驻留G基准|
|SS基准|不执行G|按冻结工作流持续执行|两专用基准与供给速率|
|SSG单批|同一目标|同输入、同步提交一批后自然结束|复现原隔离校准域|
|SSG持续|同一目标|不同输入异步到达，专用完成后持续换新|持续忙碌与混合输入的迁移差|
|SSG受控准入|同一目标|相同待处理任务，只控制启动位置和并发数|能否用有限等待换取净系统改善|

单批与持续条件同时改变了多个因素，只能先作筛查。随后应固定其中一个因素：同输入与混合输入、一次批次与持续换入、同步与错开阶段分别交叉；固定长度的prefill/decode诊断可单列，但不能代替原生成协议的效用实验。

必须评价同一外部到达cohort的所有请求。暂停启动专用会增加其等待，不能只展示G2变快；延后任务仍从原scheduled时间计时，不改到达、不丢弃任务。宏观收益仍按原Q/T/L/M/E衡量，profiler时长不混入正式无profiler收益。

## 最小采集与审计

1. 在新隔离运行中标记request_id、模型alias、输入身份、prepare、prefill、decode、postprocess、cache reclamation等可可靠识别范围；跨版本模型无法准确识别的阶段保持UNKNOWN。NVTX是host范围，需通过CUDA/CUPTI关联到设备活动；只在可识别的LLM forward边界区分prefill/decode，多模态准备不等于语言prefill。NVTX标记不添加额外设备同步；同步会改变原并发。
2. 先做小范围Nsight Systems采集CUDA/NVTX及可用OS线程事件，验证所有worker进程均被采集、request范围与GPU活动相关联、时间轴一致。若context或硬件采样无权限，明确缺失，不补猜测。
3. 先用无profiler配对估计真实时间及扰动，再对少量代表窗口采集；统计CPU API时间、GPU kernel区间并集、kernel时长分布、提交到设备执行等待、拷贝与空洞。API到kernel开始的间隔还包含stream依赖和已有工作，不能全部归为context调度；CPU同步阻塞也可能在等GPU。对比kernel除名称外还须匹配shape、dtype、输入/输出token与KV长度。重叠kernel的时间不可简单相加当GPU忙碌时长。
4. 需要硬件计数器时单独验证Nsight Compute版本/设备支持和权限。kernel replay或多pass计数可能改变并发甚至串行化，所以计数器用来解释kernel特征，不能把其采集时长当自然多进程竞争的原始性能。
5. 记录MPS、CUDA/driver、时钟/温度、运行顺序及profiler设置。受控重复与整段留出用于检验机制是否迁移，不能把相关性或一次trace作为唯一因果结论。

## 机制如何决定算法修改

- 若主要是后续专用请求持续换入，应让预测显式包含未来启动与剩余工作量，并研究路由和启动准入的联合动作，而非只加队长门槛。
- 若prefill/decode阶段组合决定减速，状态应包含阶段与剩余token工作量，建立阶段配对减速模型；总活动数模型不足。
- 若GPU执行等待而kernel自身时长变化小，应研究上下文/提交调度与启动时机；若同kernel明显拉长且有带宽或SM证据，则研究并发上限与兼容任务配对。两种机制可能共存。
- 若主要是CPU准备、同步或缓存回收，应优化这些路径并纳入端到端开销，不能靠改变GPU路由补偿host问题。
- 每个动作都要算当前G2收益、两份专用的外部延迟及后续背景任务机会成本。预测准入仍需要误差保护，最终用自身禁分流且具备同样调度能力的控制验证。

这条研究路线首先回答“共享GPU在什么组合、什么阶段、什么持续供给模式下会降低净处理能力”，再把答案编码为算法状态和动作。它可能支持更有选择地分流，也可能支持在当前配置下不分流；不能预先要求结论为正。
