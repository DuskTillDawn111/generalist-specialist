# Public181 conditional six-term prediction and prospective CPU budget

This is a new source-bound native4 path. Frozen resource-v1, expected-score-v1,
queue-only native3 and their artifacts remain unchanged. The existing eight
resource training attempts are retained. No GPU is launched by this module or
its CPU author tests.

## A testable hypothesis, distinct from a qualification

The resource training dispatcher and the new validation collector share the
actual `twoFIFO_public181_resource_execute_v1.dispatch_case` function: settled
actual eighteen-request/READY history, a ten-second settle bound, epoch at the
snapshot timestamp plus 300 seconds, every one of the original 181 arrivals,
a 90-second measurement and a fixed 120-second drain. Target workers, registry,
runtime policy, input pool, original scoring contract and candidate calendar
must match their candidate's resource donors. Source closure identity provides
provenance; differing collector hashes are not physical interference evidence.

One material activity difference remains: training waits with monitoring and
checkpoints, whereas validation additionally runs the CPU predictor, a separate
complete audit, persistence and the seal during that same startup interval.
`Hcpu_passive_training_to_live_prediction_v1` prospectively assumes this extra
CPU activity does not materially change Q, startup board energy, premeasurement
owned peak, or subsequent memory/measurement energy under those common
structural conditions. The hypothesis has **not** been calibrated or validated.
All startup energy stays in the original score; none is subtracted or omitted.
Full protocol equality is explicitly false.

A supported, complete hypothesis can therefore produce numerical Q/M/E and the
additive expected U for independent testing. `conditional_mean_available` is
separate from `source_evidence_authenticated`, empirical transfer qualification,
accuracy, original stability and final gain. The latter qualifications remain
false. A source hash, CPU author fixture, accepted seal, or passing engineering
error threshold does not establish interference accuracy or deployment gains.

Structural mismatches still block resource transfer. A missing native resource
observation or Q label keeps the original probability mass UNKNOWN. Every one
of the eight planned resource rows and all twelve queue worlds remains in its
original denominator; missing Q does not erase a known M/E observation. A seal
for target execution requires a complete six-term mean. It does not require a
previously demonstrated accuracy result, which is precisely what the fresh
validation experiment is intended to measure.

## Original arithmetic and execution boundary

Each candidate has one donor per resource block, each with weight one half.
Each donor's M uses `max(P0, future_peak)` before averaging. E includes its
same-attempt measurement-only board energy and startup energy once, amortized
at the original 3600 seconds. Q uses actual native output/reference losses and
the original offered rates. T/L/P use the unchanged twelve-world queue replay,
including each world's own P95 before averaging. Two resource blocks are not
inventively paired with twelve queue worlds. Additive expected U needs no
assumed independence; it cannot supply a probability of winning, a joint risk
law, or the original stability result.

Before worker startup, the collector opens two separately authenticated
`open_target_session` contexts. Each keeps both a concrete typed4 queue session
and an immutable native resource session alive under source-change guards.
During the original dispatcher's precase checkpoint, the producer calls
`produce`. The separate auditor calls `seal`; that call itself performs the
second full queue plus Q/M/E plus expected-score replay and exact report
comparison. There is no extra third replay. `audit_seal_structure` is a cheap
canonical receipt/deadline acceptance check after that concrete audit. Report,
gate, prefix and seal watches persist through the collector's final cleanup.
The original dispatcher checks that the durable checkpoint returned strictly
before its fixed epoch, and enqueues no target if that fails.

## Prospective evaluation declaration

`EVALUATION_PROTOCOL` is frozen in each native4 plan before validation labels.
The tolerances are **engineering bounds**, not paper guarantees, learned
confidence intervals, or statistical certification. For an observed value y,
the bound is `max(absolute_tolerance, relative_tolerance * abs(y))`.

| Quantity | Absolute bound | Relative bound |
| --- | ---: | ---: |
| Original Q term | 0.02 | 10% |
| Original M term | 0.05 | 10% |
| Original E term | 0.05 | 10% |
| Startup board joules | 30 J | 10% |
| Premeasurement owned sampled peak | 64 MiB | 10% |
| Measurement-through-drain owned sampled peak | 64 MiB | 10% |
| Measurement board joules | 90 J | 10% |

The evaluator reports descriptive errors for all six original terms; only Q/M/E
have engineering tolerance gates. It retains all four candidates and all six
pairs, including UNKNOWN rows. Observed U is the native reviewer's unchanged
original-scorer `full_U` label, verified against its original weights and term
order; a separate arithmetic cross-check never replaces that label. It reports raw predicted and observed delta U and their exact positive,
zero or negative signs, including near-zero flips. A separate absolute 0.01
indifference classification is only an engineering diagnostic and never hides
or replaces a sign disagreement. The original six terms and equal weights,
startup accounting, memory safety factor and stability rule stay unchanged.
CPU activity spans, board samples, sampling gaps, startup energy and P0 remain
available for diagnosing a failed Hcpu assumption. No post-validation tolerance
selection or model update is permitted by this declaration. Two training
blocks and one new execution per candidate cannot establish general accuracy.

`evaluate_validation` is pure error arithmetic. Its observations must first be
produced by an independently authenticated native reviewer using the original
scorer. The function explicitly does not authenticate caller-provided labels.

## New full-score CPU budget

`twoFIFO_public181_full_score_budget_v1` is separate from the frozen queue-only
budget. `benchmark(fit_report_path, public_preparation_path,
resource_manifest_path, resource_review_paths, output)` requires a real saved
matching law and all eight native resource reviews. It authenticates two law
and two resource sessions before its live proxy timing interval. A verified
training-only eighteen-request prefix seeds all four candidate proxy cases.
For each candidate the measured interval covers prefix/calendar verification,
durable prefix/gate writes, the complete producer queue+Q/M/E+six-term
composition and report write, an independent complete repeat and exact
comparison, durable seal/receipt checking, and a durable acceptance checkpoint.
Source checks and call overhead stay in the interval. An UNKNOWN shortcut
cannot establish this budget.

The predeclared requirement is `ceil(1.5 * largest measured interval) + 30s`.
The shared lead remains exactly 300 seconds; an insufficient budget holds
execution instead of extending the protocol. This is a training-prefix proxy
for execution planning: `actual_target_prefix_overhead_verified=False`, and it
never certifies prediction accuracy. The real native4 collector still checks
its actual prefix-to-seal/checkpoint deadline and releases zero target requests
if it misses that boundary.

## CPU verification scope

The expected-score tests exercise Hcpu-supported numerical predictions,
structural counterexamples, fixed UNKNOWN mass, missing quality, per-donor
memory maxima/startup accounting, real resource-session expiry, concrete
producer/seal dual passes and strict deadlines, and all-six-pair near-zero sign
flips. The timing fixtures explicitly mock saved-law/native-intake
preauthentication; complete original marginal arithmetic, dual passes, durable
IO, source receipts, budget margins and tamper rejection execute normally.
These fixtures produce no real native timing budget, accuracy result or GPU
measurement.
