# Public181: minimal native resource training and independent validation

This is a CPU preparation and producer-interface design. It adds new files;
the frozen matching and fresh181 modules and their original plans remain
unchanged. No native collector, execution permission switch, fit, GPU experiment,
prediction-accuracy qualification, or deployment qualification is supplied here.

## Why another resource interface is necessary

`twoFIFO_matching_resource_v1.DOMAIN` and `predict_timeline` deliberately require
10 s measurement plus 60 s drain, the original full physical identity, and the
original model domain before looking up a state. New90+120 cases fail that domain
gate. The identity includes implementation sources and their freeze, so merely
retaining the same models/context does not authenticate a new collector.

The memory lookup also hashes the entire ordered prior state path. A newly
generated path normally has no exact repeated key. Adding more repeated10+60
data cannot ensure that new90+120 paths ever acquire complete memory support.
The strict `twoFIFO_prospective_memory_v1` interval reference additionally keys
on exact interval duration and poll geometry; it is not the final trainable
solution. Its generated shape sidecar is reusable.

The existing `twoFIFO_case_memory_candidate_v3` is the appropriate broader
statistical direction: whole-case absolute sampled peak, fixed P0 offset, and
generated shape/concurrency features. Its legacy four-shard loader,70 s
observation domain, coefficient rank and feature support do not automatically
transfer. The four fixed public cases may give a deficient feature matrix;
inspect the feature-only design first and never force a fit or drop columns to
make these four cases appear identifiable.

## Minimum concrete campaign: eight training attempts, four validation attempts

Use the unchanged public181 trace, all four original candidate routes, exact
union22 input contents, original offered rates and objective. Retain four
resident owners, original sender/stdin FIFO, no global admission cap, and every
offered request through the full90+120 horizon.

* Training block1: one fresh startup for each of the four candidates in the
  original candidate order.
* Training block2: another fresh startup for all four candidates in reverse
  order, fixed before collection.
* Independent validation: the existing fresh four-plan design supplies the
  public cases and reserved validation identities. Its old executor is not
  silently reusable: a future native validation backend must be freshly
  prepared for the same new collection/prediction protocol as training.

Each of the eight training attempts starts fresh workers, performs the original
eighteen priming inputs once, then executes one90+120 public181 case. Thus
training has1,448 measured and144 priming requests; independent validation has
724 measured and72 priming requests. The eight new execution IDs are disjoint
from the matching15 and fresh4. Public historical request IDs remain scoped by
`(execution_id,request_id)` and are not treated as reused native executions.

The preparer binds every original arrival offset/order, owner route, task,
pool/input identity, context receipt, runtime configuration, priming semantic,
objective, and source reference. Changing a plan and updating its hash does not
pass the reconstructive audit. No target outcome is loaded during preparation.

Two training blocks are the minimum for this finite conditional empirical
baseline; four validation attempts make the requested sign/ranking test
possible. They do not establish calibrated tails, a universal resource law, or
reliable statistical confidence. More replication can follow the first
independent error report without changing the objective.

## Pre-cohort budget is part of the new resource domain

Startup energy integrates from startup begin to the first measurement arrival;
it includes loading, priming, prefix/prediction persistence and the pre-cohort
wait. The original60 s lead is not authenticated as sufficient for the new
typed bridge. A preauthenticated law package may reduce the work, but its actual
budget must still be established by the executor implementation.

The new preparer therefore requires an explicit `--precohort-lead-seconds`
argument. The CPU design instance uses300 s. This is a declared design input,
not a measured sufficient prediction budget. Training and future native fresh
validation must both use that exact new budget/protocol. Changing it requires
new preparation and a new source/protocol identity before GPU collection.
The old fresh60 s plans are public/identity references only; no equivalence of
their startup joules to the new300 s protocol is asserted.

## Resource labels: retain a joint tuple from each native attempt

The producer interface retains these four raw values together:

```
(startup_joules,
 premeasurement_owned_sampled_peak_mib,
 measurement_through_drain_owned_sampled_peak_mib,
 measurement_board_joules)
```

`startup_joules` covers startup through the first measurement arrival once.
`premeasurement_peak` covers that same startup prefix. The future peak covers
the measurement and fixed drain. Both peaks include all owned resident
processes, including inactive residents. The measurement joules cover only90 s;
drain joules remain a diagnostic. Keep all original poll brackets and live
PID/start-ticks ownership evidence. Stop monitoring before worker close.

The unchanged scorer computes

```
M = safe_factor * max(premeasurement_peak, future_peak) / memory_budget
E = (measurement_joules / 90 + startup_joules / 3600) / reference_watts
```

No provider applies the safe factor or startup amortization first. Do not add
per-owner peaks or add startup memory to the future peak. Do not average the
two peak components separately before taking the maximum: donors `(100,0)`
and `(0,100)` have mean full peak100, while max of component means is50.

Keep the actual queue/event labels and resource tuple from the same eight
training attempts for diagnostics and later joint modelling. Training outcomes
must never be relabelled independent validation. The native review must rederive
each tuple from its source raw, real ownership and lifecycle/window boundaries;
a `native=True`, `coupling=True` or receipt existing on disk cannot replace it.

## A finite supported baseline rather than an unbounded history lookup

The first resource model is an empirical tuple distribution conditional on the
exact public case and new collection protocol. Its key contains the complete
known calendar, routes, inputs, physical/runtime/priming domain and90+120
observation contract. It does not contain heldout future execution history.
Each of the two training blocks supplies one intact tuple for every candidate,
with fixed equal block weights. Its support is explicitly the four public
cases; another route, calendar, horizon, resident configuration or DFS candidate
requires another declared training domain or a validated statistical model.

This simple baseline can supply numeric M/E predictions for the four planned
independent executions. It also measures whether a more elaborate generated
shape model improves over a case empirical baseline. It does not claim unseen
input/route generalization or replace the broader algorithm's resource model.

## Initial memory is separate from a settled queue seed

The default prospective resource mode selects the whole training-donor tuple:
P0, startup joules and future peak remain coupled to that donor. No target
startup/future poll is read to build this pre-start resource forecast.

An already resident conditional mode may use an actual owned prefix, but it
must be a separately persisted, source-reviewed snapshot. Every poll must
finish at or before its explicit cutoff, and the cutoff must precede forecast
origin. A midpoint before origin with a query ending after cutoff is invalid.
Later target samples cannot repair future predictions. A settled protocol seed
contains no board samples and does not identify allocator state.

`audit_causal_prefix_polls` checks the closed clock/value interface only. Native
ownership and source derivation still require the future execution reviewer.
Do not construct that prefix by filtering the final heldout raw file after the
run and present it as a prediction sealed before the run.

## What can transfer from10+60 without pretending new data exist

An explicitly predeclared state-power stationarity hypothesis can use
`sum(P(state)*measurement_overlap)` over a new90 s generated calendar. This is
additivity over time. Board power for one state already includes the resident
baseline; adding whole-board powers across owners would count it repeatedly.
Exact input/phase/owner states still need training support and backend source
transfer must be reauthenticated. Long-run clock/thermal drift and unseen states
remain empirical issues for the new independent90 s runs.

This permits a numeric energy hypothesis for validation. It does not certify
horizon transfer or permit changing the frozen matching provider's domain.
New90+120 native data are required to validate it. Startup wait budgets must also
match; source transfer alone does not transfer startup energy.

Memory cannot be transferred merely by the additive energy argument. Its target
is a maximum with allocator/history/shape and observation-duration dependence.
The fixed-case native campaign supplies the missing90+120 memory targets. A
future statistical M model can then use generated shape/case features within
the new native feature and observation domain.

## Why expected full utility can combine marginals without invented coupling

For the unchanged equal-six objective,

```
U = -(Q + T + L + P + M + E) / 6
E[U] = -(E[Q] + E[T] + E[L] + E[P] + E[M] + E[E]) / 6
```

This is linearity of expectation; independence of resource and queue errors is
not required. The expected difference between two candidates is the difference
of their complete marginal expected utilities. Consequently a future explicit
expected-score adapter can combine the donor-only complete queue-law marginal
expectations with the two-block resource marginal expectations to test mean
DeltaU and mean ranking on these exact four cases.

Compute M within each joint startup/future tuple before averaging. Compute each
world's queue P95 using the original scorer before averaging that term; a P95
of mean completion times is a different quantity. Use the same known-input,
sampling and target execution domain throughout. Retain every unknown mass:
if any required term has unknown expectation, expected full U remains UNKNOWN.
No partial-term renormalization is permitted.

This identity does not identify `P(DeltaU>0)`, variance, tail risk, confidence
intervals, a joint generated path, or expected utility conditional on passing a
stability/memory/drain gate. Those quantities require a justified joint law or
paired native validation. Pairing resource candidates by training block is
useful provenance, not proof of resource/queue coupling. The producer never
sets a coupling Boolean to promote qualification. Original rho/g(n), stability,
memory budget and complete drain remain separately evaluated.

## Concrete producer/preparer interface

`twoFIFO_public181_resource_campaign_v1.prepare` and `audit` create and
reconstruct eight training plans and the four validation references. They verify
the frozen upstream preparation, all source receipts and the unchanged public
case. `source_transfer` binds rederived worker command/env, exact context and
new collection protocol; it expressly does not reuse the old matching physical
identity or authenticate a native backend that does not yet exist.

`forecast_request` builds a closed public-only input for a supported candidate,
training attempt roster, queue/resource model receipts and training-donor memory
origin. It accepts no target raw or future outcomes.

`paired_resource_draws` is a pure structural eight-row checker: every training
role is checked before any resource value; every planned attempt and both
complete candidate blocks are required; public case/protocol/plan identities
must match; tuples must be complete and finite. It verifies receipt bytes but
explicitly does not authenticate native collection. Future native intake must
re-run the reviewed raw/ownership/window derivation before using this helper.

`resource_bridge_payload` projects one intact tuple to the unchanged
`macro_six_term_bridge_v1.whole_score` interface. CPU tests verify original max,
measurement-only E and single3600 s amortization through that original scorer.
It does not synthesize a joint queue/resource probability law.

The next implementation step is a new source-reviewed native executor/reviewer
for this protocol, followed by a training-only tuple intake and explicit
complete expected-score producer. Reuse the reviewed runtime, ownership monitor,
fixed-calendar dispatch, lifecycle resource extractor, original scorer and
candidate arithmetic. Keep both old producers frozen. The expected-score
producer must persist predictions before the four independent target runs and
load evaluation outcomes only afterwards.
