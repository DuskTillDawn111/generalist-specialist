# Matching → kernel response continuation

New module: `tools/predictor_validation_20261027/kernel_dag_response_replication_continuation_v1.py`. Preparation and tests are CPU only; `run --manifest ... --execute` is the sole waiting/execution entry. No waiter or GPU has been started by the author.

The manifest pins the exact cpu04 producer campaign and root independent review, matching queue claim, PID/start ticks/full command, fixed matching `run-v1/report.json`, native device declaration, observed storage scenario, all three plans/contexts and complete implementation/source closure. The accepted root review schema/status are `gsdeploy.kernel_dag_response_replication_producer_independent_review.v1` and `PASS_CPU_PREPARED_NATIVE_REAUTHENTICATION_INTERFACES_NOT_NATIVE_QUALIFICATION`, with the exact campaign receipt, zero blocking findings and passing tests.

The waiting controller accepts only the pinned matching native producer's complete fifteen-attempt report plus its queue's completed final. No matching fit or rank gate is imposed. Partial JSON is waitable only while the exact original queue process remains alive; PID reuse, changed commands/source/claim, malformed final after writer exit, failed or incomplete native reports stop the chain. Immutable-source inotify guards remain active while waiting, across all three captures and CPU followups, including the matching final once published.

The producer's exclusive capture claims and original collector lease/watchdog/no-retry rules govern each of the three new lifecycles. The continuation adds a once-only started receipt before each child command and preserves every completed prefix. A started failure is never retried. All three native sessions finish before twelve sequential CPU stages: original strict native export/review, exact-source occupancy audit, original unified intake and producer instance review for each capture. Only then is the repeated-instance design frozen and the CPU alignment invoked. Every intake is rebuilt from native SQL through the new reauthentication helper; no fit is performed by this continuation.

Final path: `<prepared>/run-v1/report.json`. Schema: `gsdeploy.kernel_dag_response_replication_continuation.v1.run`. Successful native capture plus CPU completion status: `COMPLETE_THREE_NATIVE_CAPTURES_AND_CPU_DIAGNOSTICS_NO_FIT`; it records three exact capture IDs, twelve CPU stage receipts and repeated-alignment status. UNKNOWN alignment is retained as data/diagnostic output, not numerical qualification. Failure status: `STOPPED_NO_RETRY_PREFIX_PRESERVED`. Queue claim: `<prepared>/run-v1/claim.json`. The helper `continuation_identity(pid, manifest_path)` authenticates the exact run command, start ticks and manifest for a later resource continuation.

The storage scenario is derived from actual saved four-request native artifacts and serialization of new compiler rows/maps. Scaling to three twenty-request captures gives 13.171 GiB persistent and 2.494 GiB single-session temporary reconstruction, 15.665 GiB total scenario. Fixed startup/priming traces are conservatively scaled by five too. This is an estimate, not a hard upper bound. Remaining matching growth is separate. At matching completion, the waiter checks actual free space against the larger of this scenario and the unchanged collector's original 18 GiB native preflight; it waits quietly if insufficient, without creating a capture claim. Before CPU exports it rechecks the remaining export/temporary scenario. No additional 12 GiB CPU reserve is added. Temporary rebuild directories close after each capture; no historical evidence is deleted.

Seven CPU tests cover exact queue PID/claim/canonical paths, independent review gates, partial publication, PID reuse/writer exit, capacity wait without GPU claims, all twelve CPU stage interfaces and a second-capture failure that preserves the first completed capture without launching the third or any CPU followup.
