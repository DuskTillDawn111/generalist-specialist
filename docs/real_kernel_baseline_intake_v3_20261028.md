# Real metadata/light baseline intake (2026-10-28)

`tools/predictor_validation_20261027/kernel_baseline_intake_v3.py` is a new CPU-only intake/fitting tool. It leaves the frozen baseline and profiling workers unchanged. It consumes the strict three-domain bridge and independently recomputes each metadata/light semantic-group launch signature/order mapping against the canonical parsed trace and exact SQLite sources. A different group is UNKNOWN; whole-request natural timing is never used to scale individual kernel durations.

The first capture supplies 38,894 actual affine-kernel duration rows, with no missing-feature defaults and no per-kernel peak-memory targets. There are 4,164 exact categorical groups. One raw capture remains one independent run, including both text replicas and all within-capture jobs. The initial fit is UNKNOWN in all groups under the unchanged minimum of three observations across two runs.

The second actual capture supplies another 38,894 rows. Both complete canonical light-context identities equal `fc20ee9a472633fcc3d0f67dc706585cf8b7ae0f230ae249634817cfc57a7388`, while their actual raw-SHA run identities differ. The final combined fit has 77,788 observations in 4,164 groups, all with two real runs: 3,496 duration groups pass, 450 remain UNKNOWN because maximum relative training residual exceeds 25%, and 218 remain UNKNOWN because only two observations are available. Accepted groups contain 59,352 training observations. Every per-kernel peak target remains UNKNOWN. This is measured profiler-domain training fit, not heldout accuracy or a confidence bound.

Every row preserves the complete canonical light execution context, physical GPU UUID from the exact SQLite, Nsight export version, profiler domain, sampled isolation review, source SHA receipts, and real light CUPTI duration. Isolation means four resident owners with one active request; the tool verifies actual worker intervals and explicit solo jobs. Sampled absence of foreign PIDs does not establish continuous external-process absence.

Batch comes from the matched semantic-forward `input_batch_size` and must agree with the frozen execution batch. Supported implementations explicitly select `weight` for torch Linear/bitsandbytes Linear8bitLt and `qweight` for the observed ExLlama QuantLinear class. Weight bytes are that named tensor's logical bytes, never a sum over quantization auxiliaries or aliases. Precision records observed weight/input/output storage dtypes plus configured execution/quantization; accumulator precision remains unmeasured. FLOPs are enclosing operator dense arithmetic covariates, not actual per-kernel work.

Bindings retain the full actual launch signature. Regression groups bind kernel name, model family, module, implementation, operator-local kernel ordinal, and all observed non-grid launch settings. Grid may vary with workload features; this grouping does not itself supply a workload-to-grid rule. Capture pooling requires exactly equal canonical context identities, including frozen source content, checkpoint/stat receipts, actual execution configuration, instrumentation, and profiling domain. Metadata and light identities stay distinct. A copied source packet alone never creates a new independent run; actual raw captures do.

## New-pool prediction support and minimal additions

The current five feature names do not imply five-dimensional empirical support. In capture one, every row has batch 1 and every exact group has one fixed weight-byte value. There are 2,584 groups with one unique feature vector, 896 with three vectors, and 684 with two. All varying groups have affine design rank 2, so their support is a line segment in the five-feature space; point groups support only their exact point. Coordinate-wise min/max checks cannot replace the frozen estimator's affine-subspace and convex-hull checks.

A heldout pool can qualify only if its public input yields an independently justified exact shape/template instance, with the same frozen model/module, kernel algorithm, dtype configuration and launch settings, and its resulting feature vector falls inside a fitted group's convex hull. New natural-language tokens with the same input shape can be new work, but variable output length, dynamic branches, quantization dispatch and launch-grid changes still require an explicit supported mapping. Renaming a training input does not make independent heldout evidence.

The new CPU-only `chatqa_public_shapes_v3.py` maps the frozen ChatQA formatter/tokenizer input to prefill length and reproduces the observed affine shape rules; its detailed report is described in `docs/chatqa_public_shape_support_v3_20261028.md`. There is still no complete public-input-to-full-semantic-forward mapper, no independently validated unseen-input launch-grid/ordered-sequence template instantiator, and no complete affine coverage of OCR or non-affine kernels. The baseline does not manufacture these missing links. Consequently the new rows do not yet establish end-to-end unseen-pool prediction or a deployment gain. Operator metadata from executing the heldout GPU request cannot be presented as a prior forecast input.

The smallest legitimate training additions depend on each query's actual template domain:

1. Establish a CPU/public-input shape mapper and exact ordered template instantiation, with an independent reference check and explicit UNKNOWN branches. Bind algorithm-dispatch thresholds and every required non-affine kernel as well as affine kernels.
2. For a fixed point domain, obtain at least three duration observations across at least two independent actual captures. For an existing one-dimensional domain, obtain two distinct bracketing training shapes per template with at least three total observations across two captures. Existing capture repeats can supply the run requirement; they cannot add new shape support. Do not consume heldout timing for fitting.
3. Choose additional genuine training inputs so each intended heldout shape lies between measured support points inside the same algorithm/template region. Crossing a kernel algorithm or block/resource threshold starts another exact group. Batch 2 or another unobserved dimension needs new measured support; batch-1 observations cannot justify extrapolation.
4. If the desired support has affine dimension d, retain at least d+1 affinely independent feature points enclosing the query, plus the run/observation minimum and acceptable training residuals. Because fixed-module weight, tensor bytes and FLOPs are often collinear, report actual rank rather than demanding separately identifiable coefficients.

Even an accepted fit yields profiler-domain isolated duration estimates. Training residuals are not generalization confidence, intermediate peaks remain UNKNOWN, and natural timing/whole-stage overhead require separate evidence. No MPS, cross-context simultaneous-SM, achieved-occupancy or contention claim follows from this tool.

## Reproduction

Run `python -m tools.predictor_validation_20261027.kernel_baseline_intake_v3 intake --bridge <real bridge report> --output <new directory>`. Fit one or more resulting `intake.json` files with `fit --intake <intake.json> [--intake <second intake.json>] --output <new directory>`. Output paths must be new; old artifacts are immutable. The fit driver revalidates actual strict light raw/context identity and source receipts, refuses duplicate capture IDs, and retains minimum runs 2.

`tests/test_kernel_baseline_intake_v3.py` uses labelled CPU fixtures to test batch, weight selection, dtype, launch-setting, raw-run/context constraints and nested NumPy fit serialization. Together with the frozen baseline and exact bridge tests, 39 tests pass. These tests are software contract checks, never target-model evidence.

Final source-bound intakes are `artifacts/predictor-real-kernel-baseline-intake-v3-20261028-capture01-final02/intake.json` and `artifacts/predictor-real-kernel-baseline-intake-v3-20261028-capture02-final02/intake.json`. The first-capture fit remains UNKNOWN at `artifacts/predictor-real-kernel-baseline-fit-v3-20261028-capture01-final02/fit.json`; the combined fit is `artifacts/predictor-real-kernel-baseline-fit-v3-20261028-two-captures-final02/fit.json`. Exact per-group integer feature vectors and fit status are retained in `artifacts/predictor-real-kernel-baseline-support-v3-20261028-two-captures-final03/support.json`. Earlier draft and failed partial serialization outputs remain immutable; consume the final02 intakes/fit and final03 support inventory.
