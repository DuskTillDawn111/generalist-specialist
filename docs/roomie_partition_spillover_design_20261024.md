## 用户提出的资源方案应直接进入候选

“先保证专用需要的资源，再把剩余给通用”是可研究的配置，不应默认排除。必须区分：

- 时间独占：专用期间通用不执行，整卡窗口相互错开。等待要计入原到达时刻起的延迟；尚在运行的完整 generate 不能被当前接口瞬时抢占。
- 计算上限：限定客户端最大并行计算份额；不等于固定专属 SM 集合，也不保证其他物理资源隔离。
- 经验证的不重叠 SM 分区：专用与通用在不同 SM 集合发射执行。分区内的算力有限，但跨分区不再争用同一个 SM 的寄存器和 shared memory。共享缓存、DRAM 路径等还需另外考察。

NVIDIA 官方 Green Contexts 文档明确，不重叠 SM 也不自动保证并发或前向进展；MPS static partitioning 的具体支持与当前环境的工具链、运行时绑定尚需核验。不能从历史机器型号或设置了一个百分比就认定隔离已生效。

## 我们提出的联合设计

第一层，平台决定真实可执行的资源模式。先核验资源配置的效果，再给模式命名和建模：默认共享、客户端计算上限、真实不重叠 SM 分区、整请求错峰。它们不是相同强度的隔离方案。

第二层，按模式重新建服务模型。默认共享时，借鉴 Roomie 的 kernel 资源／序列对齐检查真实冲突；固定分区时，先估计各路径在其较小分区上的执行能力，再考虑共享 DRAM/L2 和主机开销。如果已验证 SM 不重叠，不应继续套用“对方抢占本 SM 寄存器／shared memory”的惩罚。占用与速度的简单反比关系必须由当前 kernel 验证，不能当普遍硬件规律。

第三层，采用 USHER 的配置联合规划思路，把模型、副本、batch、资源模式和路由放到同一候选中。共享权重共同 batch 仍作为独立后端候选保留；迁移后如实记录物理副本与逻辑并发，不更名掩盖架构变化。

第四层，在线根据可观测状态比较路由与准入动作。完整 generate 后端先做整请求控制；只有提供真实阶段事件与执行接口后才加入阶段调度。Roomie 的 placement 预测不会自动产生这种运行时能力，这是本项目需另行实现的控制层。

## 专用优先不等于给专用全部资源

专用“需要多少”应以其划分后、同背景条件下的负载能力和延迟曲线决定，而不是用显存占用或 GPU 总利用率代替。记 SM 配置为 cS0、cS1、cG、cOCR，其分配需满足平台粒度与总容量约束。两个专用放在同一专用资源池时，仍要建模它们之间的竞争；给两个副本分别分区或共同 batch 是不同候选。

若专用处理全部到达时确实需要全部计算资源，就没有可免费留给通用的计算份额。若给专用保留足够容量后通用分区尚有富余，分流可能减少排队；但通用本来的图像／ASR 等需求也要从其能力中扣除。固定分区不自动借用其他分区的空闲资源；若要弹性借用，需要额外、可执行的重配置机制和切换成本。

作为初筛，可在实测稳定状态下检查两侧总到达是否低于其配置下支持的处理能力；这种容量筛查不是尾延迟、排队可恢复性或完整 U 正收益的证明。

## 最小验证顺序

1. 保持当前驻留与输入，确认平台能实际施加哪种隔离；不在默认共享时假设已有资源划分。
2. 对少量可行资源配置测专用／通用独占活动和共跑，区分“分区导致单路径算力减少”和“共跑造成额外减速”。包含两个专用同时活动及背景请求。
3. 默认共享与真实分区各自比较分流开／关；各侧分别调优可执行路由／准入，预算相同。新模式改善不能全部归为分流收益。
4. 将实测支持的有限资源模式纳入原搜索，采用完整六项等权 U，P95 同时参与预测选择和正式评分；保留原稳定性。DFS 对同一扩展域和六项目标比较，不沿用旧域证书。
5. 单独比较预测改进、资源控制收益和最终分流收益；不存在净收益时允许算法选择不分流，不调整指标制造正收益。
