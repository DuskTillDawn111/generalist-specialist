## 1. 当前实际使用的版本

正式公式是 `six_term_reference_v2`：

```
U = -(Q + T + L + P + M + E)/6
Q = sum alpha_t * (native_loss_t - a_t)/(z_t-a_t)
T = 1 - N_deadline_success/N_offered
L = sum alpha_t * mean_e2e_t/D_t
P = sum alpha_t * p95_e2e_t/D_t
M = raw_owned_sampled_peak_memory/B
E = startup_through_drain_GPU_joules/J_reference
```

源码：[normalization.py](../gsdeploy/normalization.py)、[prediction.py](../gsdeploy/prediction.py)、[evaluation.py](../gsdeploy/evaluation.py)、[quality.py](../gsdeploy/quality.py)。

README 与 configs 中的模板仍声明 pending，但本地 11 月 4 日实验已生成 [冻结参考](../artifacts/activation-gpu-20261104/references-v2/normalization-frozen.json)、[冻结系统](../artifacts/activation-gpu-20261104/references-v2/system-frozen.json) 和[两次基线评分](../artifacts/activation-gpu-20261104/references-v2/evaluations-frozen.json)。不能据模板断言所有当前实验仍缺分母；也不能据基线评分推断新候选预测器全部适用或确认实验已完成。

## 2. 主要不足及具体证据

### 2.1 六项等权不代表六种价值平衡

T、L、P 都依赖响应时间，合计占名义系数的 1/2。它们分别表达达标比例、均值、尾部，不应仅凭相关性删除，但一次排队改善可能同时得到三项奖励。L/P 又无上界，严重延迟可压过有界 T、受预算约束的 M。

还存在分母隐含权重：`dU/d(loss_t)=-alpha_t/[6*(z_t-a_t)]`。当前相同的原生损失增加 0.01，影响如下：

|任务|ΔU|相对 QA 的惩罚倍率|
|---|---:|---:|
|QA|-0.001667|1.000|
|图像|-0.001778|1.067|
|OCR|-0.005335|3.201|
|ASR|-0.011615|6.969|

这不是计算错误；范围法明确奖励“占可实现质量跨度的改善”。但 EM 错误率、CER、WER 的一个百分点本来也不代表相同用户价值，因此不能把该表解读成应该让原生损失同权。真正的问题是项目尚需说明为什么“一个开发池跨度”值得相同代价。

建议保留现版作主基线，预声明分组对照：质量、服务、显存、能耗四组；服务组内部再划分 T/L/P。四组等权只是一个透明对照，也不是客观正确答案。已有设计中 Q/T/M/E 各 0.2、L/P 各 0.1 的五组对照只修正均值与尾部的重复，T 与延迟的共同维度仍需检查。分析候选间的分项差值、删项后排名、Pareto 支配和权重区域；分项绝对值大不等于它决定候选排名。

### 2.2 固定质量跨度有锚点噪声，输入重复不能增加语义覆盖

质量锚点基于 QA/OCR/ASR 各 32 个、图像 64 个唯一输入；最好/最弱路径又是在开发集合上选择的极值。冻结能避免随着候选扩张漂移，但不能消除极值选择偏差和小样本误差。ASR 跨度仅约 0.0359，对损失误差更敏感。

确认种子不同主要改变到达和输入排列；若仍循环同一输入池，不等于新题、新图、新页面、新音频上的泛化确认。单个完整 32 题 QA 池中，一题 EM 变化就相当于约 0.00521 的总 U 变化（其他项和锚点固定），不能把微小效用改进直接当成可靠模型质量收益。

建议将参考开发、算法调参、最终语义测试按唯一输入分开。对固定锚点下的确认收益做配对区间；另做锚点不确定性分析，重采样开发输入并对所有候选共享同一组重采样锚点。OCR/ASR 按页面/音频重采样后重新计算总编辑错误/总参考单位，不能把相关字符和词当独立样本，也不能改成逐请求 CER/WER 的简单均值。跨度不可靠时补样本，不偷偷加 epsilon 或选更差模型撑大范围。

### 2.3 两倍均值不保证相同尾部难度，也不是业务 deadline

从独立参考原始请求重算：

|任务|独立样本数|经验 P95，ms|超过当前 deadline|
|---|---:|---:|---:|
|QA|32|1034.758|2/32（6.25%）|
|图像|64|115.415|0/64|
|OCR|32|599.107|0/32|
|ASR|32|1144.417|1/32（3.125%）|

这些是用于构造分母的开发观测，不能当长期违约率或独立验证。它们说明相同倍数并不让各任务基线取得相同达标率。QA 经验 P95 低于 deadline 仍可出现 2/32 超时，涉及小样本线性插值；不能仅用经验 P95/D<1 宣称已经认证 95% 达标。

当前参考路径均为专用模型，衡量的是接近专用基准的能力。这是合理但特定的实验问题，并不天然代表用户可接受等待时间。独立参考比值与绝对用户体验应分别解释。

建议把作为归一化尺度的 `s_ref,t` 与服务目标 `D_t` 在概念和契约中分开。主版本仍保留冻结定义；新增对照预声明 k=1/2/4/8。若业务有 deadline，优先使用业务目标；若无，则称“实验 SLO”。按音频时长、页面复杂度、输入/输出长度分层报告；TTFT/TPOT 仅适用于有真实流式输出的路径，ASR RTF 也不能替代响应时间。任何新的分层 deadline 都应由请求到达时已知信息确定，不使用未来实际输出长度。

### 2.4 质量和及时性分开平均，丢失二者的关联

T 的 good 表示成功返回且及时，不要求答案正确；Q 又评价包括超时答案在内的全部成功输出。这会使“正确结果是否真正及时交付”无法从 Q 和 T 两个边际量中恢复。

例如两个 QA 方案都有 80% 正确、80% 按时，并可有相同延迟分布，但正确且按时的比例可分别为 60% 和 80%。六项在其余条件相同时可以打平。没有证据表明当前结果已经遭遇这种反例，它是指标结构的可验证盲区。

建议先新增 QA/分类的“正确且按时请求数 / 全部 offered 请求数”作为诊断，保留 Q/T 原始报告；不要简单用平均正确率乘平均达标率，那相当于假设两者独立。OCR/ASR 的及时质量价值需另外定义，不能把可能为负的 `1-WER` 无说明当作正确概率。

现版 quality/evaluation 明确要求完整成功 cohort 和 completion_ratio=1。因此失败、丢弃通常导致 U 未知/不可排名，不能声称现版已经允许通过丢弃难请求刷高总分。不过这也意味着它适合完整交付的部署比较，尚不适合公平评价容错、负载丢弃和拒绝策略；此类扩展需独立定义失败价值与删失延迟。

### 2.5 一个负载点的达标率不能说明容量和低频任务保障

T 实质是 deadline miss fraction，不是最大吞吐能力。在较轻负载下多个方案都接近 T=0，潜在容量差别不可见。Q/L/P 用名义 alpha，T 用实到请求比例；短 Poisson 轨迹中两种任务混合并不完全一致，应报告实际任务计数，必要时另报按任务固定权重的 miss rate。

建议在固定流量混合下扫描到达率和突发程度，报告各任务达标曲线、goodput、队列增长与最大可持续到达率。可预声明一个达标水平 tau，估计所有任务均达到 tau 的负载上限，同时保留连续质量结果；不能把新 tau 混入旧版资格标准。按流量加权适合平均请求价值，但应同时列每任务值和最差任务值，避免低流量任务退化被平均隐藏。

### 2.6 M/E 对资源价值的解释仍有限

M=峰值/容量准确表达空间压力，但同样的峰值可能是一瞬间 workspace，也可能是全程驻留；低于容量后的每 MiB 是否值得线性扣分取决于显存是否可用于别的部署。DRF 的资源份额并不证明它是一个线性经济成本。

建议保留峰值和安全约束，补充驻留显存、时间平均占用或 MiB·s 诊断；若以后采用资源价格，应由容量机会成本或明确偏好确定，不能事后拟合有利排名。

E 的完整 episode 边界比旧版更完整，但结果依赖 H，且仅测 GPU 板卡。CPU OCR 前后处理、音频解码、主机内存、模型加载 I/O 的能源可能遗漏。共同基线 J_ref 也会改变能耗相对于其他项的有效权重，即便所有候选使用同一个分母，仍可能改变综合排名。

建议同时报告 startup/formal/drain 的 J、固定工作负载下的总 J、稳态功率和有效交付能效。短任务与长期常驻分别评价；资源允许时测完整系统能耗。没有新遥测时继续明确称 GPU 能量。

### 2.7 当前点估计不能支撑微小收益结论

同一纯专用开发基线两次 U 分别为 -0.512128 和 -0.521334，相差 0.009206。其输入计数、到达轨迹、质量加权和实测延迟均有变化。两个样本不能估计可靠噪声下限或置信区间，更不能规定所有低于 0.0092 的收益都无效；但足以说明跨种子单次总分比较不可靠。

建议同一候选与对照共享 offered trace 和输入，执行顺序交错；按独立运行重复配对估计 ΔU。质量泛化与系统随机性分别采用唯一输入层和运行层重采样；排队时序不能简单逐请求独立 bootstrap。报告各项 ΔU、区间、实际改进幅度与最差任务退化。先以开发数据确定精度/预算和确认规则，再冻结最终确认，避免反复追加直到出现正收益。

## 4. 建议的最小改进顺序

1. **先保持 v2 可比，补报告。** 对全部候选保存六项原始量/分项差、每任务质量与达标率、资格状态、配对 ΔU 与区间；核对模板与实际冻结配置身份。展示 Pareto 集，主 U 仅代表声明的折衷。
2. **完成敏感性与不确定性审计。** 预声明 k=1/2/4/8、现有六项等权、五组对照和四组对照、质量相对最佳对照；先对可重建的既有记录复算。改变目标后需要重新搜索才可声称新目标下最优，固定候选重评分不能替代重新优化。
3. **增加联合交付指标和压力实验。** 先对 QA/图像实现正确且及时比例，补所有任务按负载/输入复杂度的分层曲线。保留完整成功 cohort 版本边界。
4. **用独立证据选最终目标。** 根据业务偏好与跨负载稳定性决定是否发布 v3；新目标须重新核查预测器、界、剪枝和搜索证书。若某方案只在狭窄权重区间获胜，论文应报告其适用偏好，不能概括为全面更优。

最有价值的目标是让“为什么选这个部署、对什么用户需求有益、在哪些负载成立、改进是否超过测量不确定性”都能回答，而不是再找一个复杂归一化函数。
