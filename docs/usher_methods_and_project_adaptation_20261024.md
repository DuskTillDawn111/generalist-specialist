# USHER 方法逐项复核与当前系统的具体改造

日期：2026-10-24。本文补充之前的文献综述，不改写冻结实验、指标、算法或已有收益结论。本轮完成原文方法与消融复核、现有代码对照和工程设计，未复现作者运行时，未运行新 GPU 实验。

## 1. 先纠正之前的提炼

此前主线把 USHER 主要概括为“联合考虑副本、批大小、放置，并通过画像预测共跑代价”，没有把其主动改变执行的两条核心链展开：

1. **按配置估计资源需求 → 互补分组 → 联合搜索 BS/RD → 多维装箱和实际资源分配**，在其资源模型下避免计算／内存需求超配。
2. **图结构分组 → 算子匹配 → 提取公共权重子矩阵 → 输入拼接与算子重构 → 单 context 执行**，使公共权重在缓存内被多个输入及时复用，减少缓存竞争。

所以，已经引用、概括这篇论文，不等于已经把它的抗干扰机制落实到我们的系统。尤其不能把“预测负收益后拒绝分流”当作论文全部启发，也不能用“当前接口不同”直接跳过资源控制和算子合并。

## 3. USHER 如何减少竞争：完整机制

### 3.1 GK-Estimator：资源需求取决于执行配置，不是模型大小标签

论文先离线获得 ONNX 算子到 GPU kernel 序列的对应关系，新模型转换为 kernel 图。回归器使用 BS、权重张量大小、输入中间张量大小、FLOPs 与 GPU 类型预测 kernel 执行时长和中间数据需求。时长预测用来识别可能并发的 kernel 集合；开始时间差不超过 τ 的 kernel 被视为可能同时执行，论文取 τ=0.001ms。

对顺序模型，论文将参数大小与最大算子中间数据需求相加；对分支模型，对各可能并发 kernel 集合求中间需求之和，取最大值再加参数大小。其含义是估计给定配置的资源峰值，不是把每个算子的需求全部累加。

两个边界必须保留：

- 回归特征明确不依赖同卡其他模型的 kernel，所以这不是任意异步共跑减速的直接预测器；系统还依赖后续资源分配与缓存优化。
- 并非完全不需要 GPU 数据：算子／kernel 映射与回归训练需要离线采集，论文报告 V100 上训练约 1.3 小时。其 99.98% 是论文指定模型和配置下的报告值，不是可继承的误差界。

论文对 Mreq 的正文以显存空间／中间数据峰值解释，但实现段又写用 `dram_utilization` 测量 Mreq；Creq 的实现涉及 `achieved_occupancy`。迁移时必须分别记录**显存容量、DRAM 吞吐、SM 活跃／占用和 L2 行为**，不能将这些物理量相互替代，也不能把占用百分比线性当作算力百分比。

### 3.2 工作量划分：联合决定批大小、副本和放置

论文 §2.2 的 RD 是把请求划分到多个 GPU，每个 GPU 复制整个模型。缩小每份的 BS 可以降低中间显存需求，虽然会复制更多参数，却可能让不同模型更紧密地放入更少 GPU。是否有收益必须同时考虑所有模型，而不是每个模型各自选最少副本后再拼起来。

算法 1 在每个模型组中枚举所有模型的 `(BS, RD)` 配置；论文 BS 集合是 `{4,8,16,32,64,128}`，RD 是满足 SLO 的最小复制度的 1–6 倍，固定集群还受 GPU 数量上限约束。每个配置调用算法 2 放置，之后依据对应目标选配置。

因此，它联合改变的是**每份工作量、批执行形态、资源峰值和模型放置**。同卡增加独立进程不等于复制一块 GPU 的计算能力，也不能把当前两个同卡专用副本直接说成已经实现 USHER 的跨卡 workload division。

### 3.3 IR-Scheduler：互补分组、多维放置和实际分配

论文先按不同 BS/GPU 组合下的平均需求分组，目标是组内 `ΣCreq ≈ ΣMreq`，通过迭代两两合组将组规模保持适中，例如最多 4 个模型。这一步缩小后续联合枚举空间，同时增加计算重／内存重模型配对机会。

算法 2 进一步执行：

1. 对当前 BS/RD 配置计算各模型在各类 GPU 的需求，超过最大 GPU 容量则判不可行。
2. 用需求比 1.2 区分计算重和内存重模型，分别按 `Creq+Mreq` 从大到小排序，再交替放置；中间类型按总需求顺序插入。
3. 优先放到本模型组已经使用的 GPU；其次其他组已有 GPU；不足时开新的最低成本可用 GPU。
4. 多个 GPU 都能容纳时，选放入后剩余 `C-space+M-space` 最少的 GPU，减少资源碎片。
5. 计算含排队时间的 goodput；弹性集群在满足 SLO 时选最小成本，固定集群选最大 goodput。

§4 写明实际用 MPS 按需求划分计算资源。这里是**有配置、有需求、有执行约束的共置**，而不只是“发现两个队列一忙一闲”。但是论文的“C/M 无干扰”依赖需求模型和资源分配假设，不能据此保证任意 MPS 百分比消除了全部硬件干扰。

这种分组、组内枚举加启发式放置，不提供我们整个七模型部署／路由域的全局最优性证明。

### 3.4 为什么还需要 OG-Merger，而不能只分资源

§3.1 明确说，IR-Scheduler 不满足每个模型的独立 cache 需求，因为其测试中该需求接近整个 cache；若按每个模型都需要的 cache 额度强行分配，会浪费计算与显存空间。因此作者单独设计 OG-Merger，提高缓存内容的共同使用效率。

这回答了“分好计算资源后为什么仍会竞争”：**计算份额的分配和缓存复用是不同层次的控制。** USHER 没有把分配计算份额当作全部问题的终点。

OG-Merger 的具体过程是：

1. **结构分组**：同卡模型按图编辑距离，通过 DBSCAN 找结构相近的组。
2. **算子建边**：同类型、预测开始时间相同、权重相似度达到 ω 的算子才能匹配；论文实验选 ω=40%。
3. **最大权匹配**：将两张算子图组成二分图，用 Hungarian 算法选择互不冲突、总权重最大的算子对应，再逐步并入其他模型。
4. **公共子矩阵提取**：找到最大的公共权重子矩阵，论文把元素绝对差不超过 `1e-7` 视作相同；尺寸不同时先补零。
5. **重构执行**：建立公共矩阵 `Ws` 和各模型残差矩阵，将不同输入拼在一起，对公共部分发射一次 GEMM，然后计算各自残差并还原输出。

在公共子矩阵位于相同索引的简化情形，公式是：

```text
W1 = Ws + R1,      W2 = Ws + R2
Ic = [I1, I2]
Ys = Ws @ Ic = [Ws @ I1, Ws @ I2]
Y1 = Ys[:, :n1] + R1 @ I1
Y2 = Ys[:, n1:] + R2 @ I2
```

这是说明数学关系的伪代码，不是当前后端可直接运行的实现。公共子矩阵索引位置不同时，原文还要求重排对应输出；其图 11/12 给出了相关节点。

关键收益不是“数学上只算一个输入”，而是让两个输入在同一个 GEMM 的执行组织中及时复用公共权重。不同输入的乘加仍然存在，模型所有权重也不需要同时装进 L2。**仅让两进程指向同一权重存储，没有同步组织这些矩阵运算，不等价于论文的 cache-aware merging。**

合并图再优化，作为一个 CUDA context 在 MPS 中执行，获分配原图计算份额之和。不是保留多个独立 `generate` 黑盒后，仅加一个“共享权重”开关。

### 3.5 消融也说明，算子合并不是次要附录

§5.5 分别去掉计算重／内存重区分、额外 workload division、需求排序和 OG-Merger。指定实验中，完整 USHER 比去掉 OG-Merger 的版本 goodput 高 55.7%。这是论文特定设置下的消融，不能预言我们的收益，但足以说明此前只强调规划、略过执行图改造，会遗漏重要方法。

§5.6 还说明 ω 太高会失去合并机会，太低则额外操作开销抵消收益。合并不是越多越好，需要计算拼接、补零、残差、重排和等候配批的净代价。

Table 2 把分组、调度、模型加载、图合并分开列开销。论文先用原图服务，再在合并完成后切换；合并不应被错误地计成每个请求都要支付一次，也不能从系统成本里完全省略。

## 4. 当前系统缺的不是一个更复杂的分流阈值

当前研究驻留为两个文本专用副本、G2 和 OCR，同卡运行。`CoupledUtilityPolicy._terms` 已比较同一 completed+pending cohort 上的 Q/T/L 和剩余板级 E；`CoupledEventModel` 会在活动集合变化时重新估计活动请求。不能把这些已有能力说成新从 USHER 引入。

缺口在执行与资源控制：各 worker 执行独立完整 `generate`，尚无已验证的按需求资源份额、共同 batch 执行、算子合并或统一阶段调度。因而目前主要是在已有执行形态中选路，尚未实现论文那种通过配置和图变换降低干扰的系统。

已有 401/402 取证发现，分流节省了排队，但 G2 自身服务及其他请求代价抵消了它；相同输入的 G2 独占参照并不天然更慢。**这些证据支持把共享执行代价作为重点，而没有证明慢因已具体定位到 L2、SM 或带宽。** 原 handler 重叠不是 kernel 重叠。

## 5. 真正借鉴到本项目的三个改造

以下是本项目方案，尚不是已实现／测得有效的功能。

### 5.1 把资源配置放进部署候选，按同一个目标搜索

原候选主要决定模型、副本和路由；扩展为：

```text
候选 = 驻留模型及物理副本数
     + 每个执行单元的 batch/token/workspace 上限
     + 平台实际支持的计算资源配置
     + 可执行的并发准入规则
     + 是否启用共享权重／共同 batch 后端
     + 请求路由策略
```

其中计算配置的物理含义必须实测核实，不能将一个 MPS cap 当作已经预留独占 SM、L2、DRAM 带宽。先画像受支持的小集合，合并后的模型重新画像；其他资源状态仍为 UNKNOWN，不推断成线性缩放。

按 2026-10-24 用户最新要求，后续采用完整六项等权效用 `U=-(Q+T+L+P+M+E)/6`，P95 正式参与总效用，原稳定性不变。契约见 `configs/resource_spillover_objective_20261024.json`。资源配置若降低 G2 争用，却使专用积压增加，仍可能被完整目标否决。

USHER 的互补排序／组内规划可作为找候选、找好 incumbent 的启发式，不能据其启发式分组直接删掉原本需要证明的全局域。DFS 必须比较同一扩展域、同一个预测器、同一目标；旧域的最优证书不继承。

### 5.2 优先研究两个相同文本专用副本的共同执行

先核验两个副本的 checkpoint、adapter、量化元数据和权重张量身份。若有效权重完全相同，则公共权重不只是一个局部子矩阵，而是更直接的共享机会：将独立请求放入同一权重实例下的共同 batch 执行，保留每个请求独立的 KV、位置与输出状态。

必须区分三件事：

1. **权重存储去重**：减少权重驻留副本，但未必降低运行中的缓存争用。
2. **同权重共同 batch 执行**：组织不同输入在同一层矩阵运算中使用同一权重，是比只去重更接近 OG-Merger 缓存复用目标的办法。
3. **原论文跨模型部分矩阵合并**：仍需要图和权重匹配、残差／重排操作，不可把第 2 项冒称完整复现第 3 项。

两个独立进程转成一个共享权重执行单元，会改变物理副本数与服务后端，不得把“两个逻辑并发请求”仍记录为两个物理副本。它应作为新增候选，与原双副本保留对照，不悄悄改原实验定义。

不同输入不能因此共享 KV，也不能把不同模型的 KV 混用。当前长输入短输出条件下，共同 batching 是否有净收益仍取决于补齐、配批等待、显存峰值、量化 kernel 支持和真实阶段构成。

### 5.3 对通用／专用做真实互补分配，而不是假设它们天然互补

G2 与文本专用不是同一基础模型／量化实现，不能只因都是 Transformer 就套用论文权重重合率。先检查真实层结构与权重；没有公共部分就不做跨模型 OG 合并，转用需求感知的资源配额、batch 和并发控制。

计算重／带宽重标签也需按输入长度、batch、执行阶段和资源模式分别测。若同阶段争用严重，允许错峰准入；若互补共跑更好，再保留共跑。按整次 `generate` 控制只能叫整请求准入；prefill/decode 控制需要后端提供实际阶段动作。

一次分流的评价须同时包括：本请求少等多久、它在 G 上的服务时间改变、所有受影响专用请求、G 的图像／ASR 机会成本，以及 M/E。必须比较资源控制后的最佳禁分流方案，不能把资源控制本身的收益全部记成分流收益。

## 6. 能直接回答问题的有限实验，而非重测所有混合组合

先固定现驻留与输入分布，用一个小机制集合回答“哪项措施改变了竞争”：

|执行模式|要区分的机制|公平对照|
|原双专用独立执行|现状基线|原路由开／关|
|双专用共同 batch／共享权重执行|权重重复加载、缓存复用与批效率|同到达和生成协议的独立执行|
|可执行的需求感知资源配置|计算份额变化与跨模型干扰|相同后端、相同驻留、无该配置|
|准入错峰或经证实的互补共跑|持续启动／阶段碰撞|同能力禁分流方案|

上述模式是机制集合，不是宣称所有交叉组合已实现。共享后端与分区应先做兼容性、正确性与资源检查。机制筛查后只将有支持的少量配置纳入搜索，不对任意组合开 GPU 全枚举。

采集同工作量条件的 device timeline；有可靠支持再采 L2/DRAM/SM 指标。区分 kernel 等待与执行、CPU 准备／同步／回收；记录配批新增等待。正式性能使用无 profiler 的交错重复，profile 窗口用于机制解释。

最终四角对照为：原后端禁分流、原后端允许分流、新执行控制禁分流、新执行控制允许分流。新后端内允许／禁止分流之差才回答“降低竞争后分流是否有净收益”。共享后端、资源配置、配批策略的调参预算两侧一致；无正收益也如实报告。

## 8. 与提前分配的关系，以及正分流收益的判别

### 8.1 两者可组合，但按执行单元确定边界

提前分配控制各执行单元能够使用多少资源；共同 batch／算子合并改善一个执行单元使用这些资源的方式；准入调度控制何时进入执行；路由决定请求去哪个单元。

可以先为专用组、通用组和必要背景服务建立经过核验的资源配置，再在专用组内研究同权重共同 batch。这样不需要跨越专用／通用分配边界。跨组算子合并则会形成新的联合执行单元，需要重新分配该单元的资源，不能同时声称同一个融合 kernel 仍分别运行在原两个独立硬分区里。

提前分配应作为核心研究变量和对照，不预设最终最优一定永久锁定某比例。动态 cap 与独占资源分区要分别记录；只分 SM 不意味着 L2、DRAM 带宽和功率全部独立。平台未支持的分区或运行中重分配动作不进入可执行候选域。

### 8.2 降低干扰不等于创造更多物理算力

严格分区可以减少计算资源争抢，也可能让单次请求可用的 SM 更少；固定留给通用但不可借用的资源还可能闲置。其净收益取决于“少受干扰”能否覆盖“少用算力”和调度开销。

同权重共同执行可能降低重复权重读取和提高批执行效率，但新增配批等待、padding、workspace 也可能增加。专用本身变快后，专用队列可能缩短，分流的边际收益反而下降。优化系统成功与分流比例上升不是同一目标。

### 8.3 当前证据支持验证机会，尚不足以承诺稳定正收益

现有同输入独占参照里 G2 比专用平均快约 192/253ms，而实际共跑 G2 服务反而多用约 1101/1207ms。这给降低共享执行代价提供了值得验证的空间，但前者是原条件下的参照；给 G2 固定较小份额后必须重新测，不能直接沿用独占速度。残差也含 host／同步等，尚未证明都是 GPU 硬件竞争。

延迟维度需同时计入分流请求少等的时间、自身服务变化、所有其他请求等待／服务变化及新增控制开销。按最新六项契约，完整判据为同一到达 cohort 的 `ΔU=-(ΔQ+ΔT+ΔL+ΔP+ΔM+ΔE)/6>0`，不把毫秒、质量和能耗直接相加。质量按原规则扣分，P95 进入 U，稳定性不改变；P 必须从各候选的完整任务延迟集合重新求分位，不能把请求分位数变化直接相加。

严格的额外分流价值应比较：

```text
max U(允许分流；资源配置、后端、准入可优化)
    - max U(禁止分流；同样的配置、后端、准入选择和开发预算)
```

若把同一份资源交给专用更好，算法应增加专用资源，而不能通过压低专用份额制造分流收益。通用还必须履行图像／ASR 等背景义务，其机会成本进入评价。只有存在可利用的通用剩余处理能力、资源互补或不同扩展效率，并足以抵消质量与资源成本时，才有严格正收益的机会。

允许分流的策略域若包含“不分流”，则在相同精确评价器和完整同域搜索下，预测最优值弱优于禁分流；这不保证严格正收益，也不保证有误差的在线策略实测不退化。

### 8.4 下一轮以有限机制对照决定是否扩展

先在现有双专用部署上验证实际支持的资源分配和持续供给表现；随后单独测共同 batch 后端，最后测二者组合。各执行条件均允许／禁止分流成对比较，并允许禁分流侧自行选最优资源份额。这样可以识别资源分配本身、共同执行本身及剩余分流的贡献，不必在尚无机制证据时枚举所有交叉配置。

冻结开发选出的配置后，用独立负载重复验证全体请求效用及原稳定性。有限扩展域再交给搜索与同域 DFS 核验；不把机制降时延直接称为已获得稳定六项效用收益。
