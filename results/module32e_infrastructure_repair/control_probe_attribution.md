# 控制检查异常归因

原控制检查是module31a.campaign.TimedMonitor.check包裹SafeMonitorV2.check；开始和结束均用同一host perf_counter单调墙钟，包含获取state_lock、读取错误元组和检查error/resource/foreign事件的时间。它不是GPU执行时间、不含CUDA synchronize，不应与worker service或E2E相混。原门槛是整个运行所有check及phase_publish样本的最大值严格小于0.01秒；32E原样保留，不放宽。路由计时另为完整runtime.lock获取+状态投影+policy.decide+enqueue，P95≤1ms。

32D E0_S实际日志保存max_check=19.360993ms、max_publish=0.488940ms，snapshot runtime锁最长约0.244403ms；控制检查原始逐样本时间戳和锁owner没有保存，无法唯一识别19.36ms的具体时刻或全部调度原因。历史CPU修订不等于GPU通过。

源码中的直接异常路径：32D v1 IncrementalMonitor.coherent_records进入state_lock，获取runtime锁更新cache，离开runtime锁后在return表达式执行完整cohort deepcopy，直到return完成才退出state_lock。这把copy期间的GIL/内存分配和线程调度扩展成主线程check的锁等待。注释只保证copy在runtime锁外，并未释放控制state_lock。journaling/fsync本来在两锁外；不能把所有延迟归咎于NVML或磁盘。旧SafeMonitor拷贝曾发生在10秒interval判断之前，32D已将interval判断前置；32E保留这一修复。

CPU证据：读取32D真实281请求及其worker payload并重放上述copy临界区，12次旧路径检查mean约14.37ms/max约15.30ms；修复路径最大约0.0074ms。读取32C真实3419请求长窗口cohort，旧路径8次最大约292.89ms，修复最大约0.0089ms。这里只做CPU工程复现，没有人为延长GPU服务或制造效用。记录每个wall、thread CPU、state lock wait/hold值，保留全部超限样本。旧路径随着快照payload增大而加重，支持锁范围问题；不能将复现值当作历史那一次outlier的精确归因。

32E监测器采用32D CPU v2方案：state_lock内仅捕获active/cache/order引用，runtime锁下处理增量事件及活跃状态，深拷贝、序列化、fsync都在控制锁外。切换phase时用runtime锁下的指针校验，禁止迟到旧phase快照消耗新phase终态事件；针对测试通过。CPU event-gated阻塞sensor/durable IO时，检查仍可完成；这是可控CPU故障测试，不代表未来GPU永不调度暂停。并发sender/collector+0.5秒采样+10秒fsync完整回放还保存control时序及路由锁等待，所有检查低于10ms。

新GPU逐次保存check的单调时间戳、wall、thread CPU、state wait/hold、phase和thread，另保留温度/功率/频率、host RSS/worker CPU、native请求执行与queue时间、完整journal。测量值达到10ms就立即禁止下一次准入并停止预检，保留整批计划请求和全部异常值。只有真实GPU预检也通过后才能给基础设施ready Gate。
